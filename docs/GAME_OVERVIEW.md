这份文档写给两类读者：想一次看清“现在这个游戏里到底有什么”的项目负责人，和之后接手继续开发的人（或 AI）。

## 1. 一句话与一分钟

**一句话**：掷骰子凑牌型的肉鸽构筑游戏——像扑克牌构筑游戏那样靠被动卡叠倍率，但手里的“牌”是可以被永久改造的骰子。

**一分钟**：一局 24 关。每关给你 3 次提交机会，每次提交前可以掷 3 次骰子、挑一些锁定，再把锁定的骰子按顺序提交计分；累计分数达到本关目标就过关。
过关拿金币进商店，买“控制器”（被动卡）、道具、牌型升级、骰面改造、新骰子和各种服务，然后进下一关。
关卡每三关一个周期：普通关、可选加码的高压关、带一个减益的首领关；打过首领有一份免费战利品。打完第 24 关通关，任何一关分数不够就失败。

| 项 | 现状 |
| --- | --- |
| 版本 | 规则 p1.0.0 / 存档结构 6；预发行 [p1.0.0-rc.1](https://github.com/XDwudi/game2/releases/tag/p1.0.0-rc.1)，分支 `codex/v1.0` |
| 引擎与平台 | Unity 6000.6.7f1（URP，Mono）；Windows x64 与 macOS Universal 出包。macOS 包从未在真机上启动过；移动端只是长期意图，没有任何实现 |
| 内容量 | 控制器 150、道具 12、商店服务 11、骰面改造 11、首领减益 39、战利品 6 种、牌型 13 + 颜色牌型 2、附魔 5、关卡 24 |
| 美术 | 高清简约的“复古印刷骰桌”风格（v0.72 / v0.73）；184 张内容插画；立体骰子 |
| 状态 | 原型（P0）。自动化测试齐全，**从未做过真人试玩记录**；所有“好不好玩、难不难”的结论目前都来自机器人模拟 |

## 2. 一局游戏的流程

```
新建挑战（输入或随机种子）
  └─ 关卡选择页（看本周期三关：目标、首领减益、战利品；高压关在这里选是否加码）
       └─ 对局：每关 3 次提交
            每一手：掷骰（最多 3 次）→ 点选要留的骰子 → 确认锁定（本手不能解锁）→ 调整提交顺序 → 提交
            达标后可以继续提交，也可以“结束本轮”把没用的提交次数换成金币
       └─ 结算（过关金币、剩余提交奖励、利息、控制器收益、首领战利品预告）
       └─ 商店（买卖、升级、改骰、服务；可查看接下来三关；首领关后领战利品）
  └─ 下一关 …… 第 24 关通过 = 胜利；任何一关提交用完仍未达标 = 失败
```

几个容易忽略的规则：

- **锁定不可逆**：确认锁定的骰子本手不能放回骰池，只能调整它们在提交栏里的顺序。没锁的骰子可以继续掷。
- **提交顺序有意义**：很多控制器看位置（第一颗、最后一颗、相邻关系、左右对称）。
- **不提交的骰子也有用**：留在骰池里的骰子叫“留池骰”，一整类控制器读它们。
- **达标是锁存的**：分数一旦达标就算过关，之后的提交只为刷成长、赚提交收入，或者直接结束拿剩余提交奖励。
- **整局确定性**：骰子、商店、效果、关卡计划各用一条独立的随机流，同一个种子加同样的操作一定得到同样的结果（存档、回放、模拟都依赖这一点）。

## 3. 计分

得分 = **基础分 × 牌型倍率 × 颜色倍率 × 红组倍率 × 各控制器倍率 × 附魔倍率 × 道具与首领系数**，最后向下取整一次。全程用精确的大整数有理数计算，没有浮点误差。

| 乘区 | 来自哪里 |
| --- | --- |
| 基础分 | 每颗提交骰的点数贡献（点数 → 逐骰加值 → 逐骰倍率 → 玻璃 ×3 → 黄金面 ×2，可被“再计一次”重复）之和，加未用投掷奖励（每次 +3），加各种整手加值，加“基础分增加”附魔（每个 +10） |
| 牌型倍率 | 同点牌型（一对 ×2 …… 八豹子 ×40）与顺子（×10）可以同时成立、倍率相加；可用金币升级，每种最高 8 级；什么都没有是散点 ×1 |
| 颜色倍率 | 提交的骰子全蓝 ×3、全红 ×2（可升级） |
| 红组倍率 | 提交里红骰越多越高：2 颗 ×1.75 …… 5 颗 ×5 …… 8 颗 ×14。标准骰只有 1 点和 4 点是红面，所以红是“难凑但回报高”的颜色 |
| 控制器倍率 | 各张卡的 ×N，按控制器从左到右连乘 |
| 附魔倍率 | 带“倍率增加”附魔的卡触发时再 ×2 |
| 其他 | 道具灵光一闪 ×2；个别首领减益 ×1/2 |

骰子本身的属性：六个面各有**点数**（1–6）、**颜色**（红 / 蓝）、**纹理**（光滑让对面更少掷出、粗糙相反）、**是否黄金面**、**权重**（越大越容易掷出，上限 5）；整颗骰子可以是**玻璃骰**（贡献 ×3，但每次投掷有 8% 概率永久碎掉）或**临时骰**（本关结束消失）。
开局 5 颗标准骰，最多 8 颗永久骰；提交栏开局容量 5，最多 8。

精确的计分顺序（十步）在 [v1.0 规格](specs/v10/RULES_SPEC.md) 第 5.2 节。得分明细界面会把这条链逐项展示出来。

## 4. 控制器（被动卡）

控制器是这个游戏的构筑核心，共 150 张，三种稀有度（普通 30、罕见 89、稀有 31），价格 2–8 金币。普通栏位开局 5 个，可扩到 7 个；带“不占栏位”附魔的卡不占普通栏位；总件数上限 10。

每张卡在商店出现时可能带一个**附魔**：不占栏位、基础分增加（+10）、倍率增加（×2）、提交增加（每关 +1 次提交）、投掷增加（每手 +1 次投掷）。

**三批内容：**

| 批次 | 编号 | 特点 |
| --- | --- | --- |
| 基础 50 张（v0.6） | C01–C53（缺 C04、C16、C23） | 条件倍率（只要奇数、2233、对对穿肠、三条开泰……）、逐骰加值、规则改写（简单顺子、不要奇数、简化提交）、骰面永久效果（骰子复制、红色扩散、不断成长）、经济（存钱罐、成长基金）、特殊（百变模仿、玻璃大炮、控制欲、错乱乘积） |
| v0.9 的 50 张 | C54–C103 | 成长型（卡随对局变强）、再计一次、留池骰、投掷阶段（一锤定音、孤注一掷）、牌型专精、骰面协同、经济、牺牲与取舍（祭坛、双刃剑、精兵简政） |
| v1.0 的 50 张 | C104–C153 | 提交顺序 6、随机生成 7、骰面长期养成 12、首领与高压 5、道具与临时骰 4、金币 4、牌型与流派 9、构筑 3 |

**几个贯穿全局的机制：**

- **成长值**：成长型卡带一个随对局累积的数（每次提交、每过一关、每买一次改造……），倍率 = 1 + 0.05 × 成长值，或直接加基础分。
- **再计一次**：指定的骰子点数贡献再算 N 遍，与逐骰加值、玻璃、黄金面相乘。
- **百变模仿（C41）**：复制右边相邻控制器的完整技能；进关时绑定目标，关内不变。
- **非计分类**：经济、随机生成、规则类的卡不参与“触发”，不会带基础分 / 倍率附魔。
- **骰面永久变更**：v1.0 起，卡可以在每次提交后或每关结算时永久改写骰面（点数、颜色、黄金、纹理、权重）。
- **失效**：首领减益可以让某些控制器本关完全没有技能（也不成长、不产生收益）。

**现有流派**（详见 [强度与体验分析](specs/v10/BALANCE_REPORT.md) 第 5 节）：同点 / 豹子、对子与 2233、顺子、全蓝、红组、小点数（全 1）、大点数（全 6）、全 5、黄金面、玻璃、留池、单骰、成长、经济 / 金币、道具、提交顺序、首领专精、少而精（留白）与多而杂（控制欲、草根逆袭）。

## 5. 商店与经济

商店是单页布局，从上到下：控制器货架（4 张，可扩到 6）、道具（2 件，可扩到 5）、牌型 / 颜色升级（2 个报价，另可“自选研习”2 次）、骰面改造（2 项）、服务（2 项）、新骰子候选。v1.0 新增右上角的“查看关卡”与“首领战利品 / 商店赠礼”。

| 类别 | 内容 |
| --- | --- |
| 道具（12，一次性，背包 2 格可扩到 5） | 改颜色（红色 / 蓝色浪潮）、加资源（临时骰子、增加提交、增加投掷、扩容符）、控骰（遥控骰子、大数 / 小数多来）、加分（灵光一闪 ×2）、养骰（点金笔）、应对首领（破咒符） |
| 骰面改造（11，永久） | 纹理（光滑、粗糙）、染色（染红、染蓝）、材质（脆化成玻璃、黄金电镀）、点数（随机变形、精雕 +1、削点 −1）、配重、镜像（复制到对面） |
| 服务（11，局外能力） | 扩容类（道具槽、货架、控制器栏位）、道具打折、加入 / 删除骰子、免费刷新、贿赂首领（重抽减益）、理财顾问（利息上限）、附魔台 |

**金币来源**：过关 5（高压挑战 10）；每剩 1 次提交 +1；利息每 5 金币 +1（本金上限 25，可提高到 45）；经济类控制器；首领战利品折现 5。
**金币去处**：买卡、升级（越升越贵：基础价 + 已有等级 × 2）、改骰、服务（多数越买越贵）、刷新货架（3 起每次 +2）。控制器按标价的一半回收，同名卡可以“以旧换新”。

## 6. 关卡结构（v1.0）

- **24 关 = 8 个周期**，每个周期：普通关 → 高压关 → 首领关。目标分从 300 涨到 2000 万（环比 ×1.3–×2.0）。
- **高压关**：进关前自选“普通挑战”或“高压挑战”（目标 ×1.5，过关金币 10 而不是 5）。
- **首领关**：带 1 个减益。第 3–21 关从 30 个常规减益里抽，分三档，越往后越重、一局内不重复；第 24 关从 9 个终局减益里抽。**整局 8 个减益与战利品种类在开局时就定好**，关卡选择页和商店都能提前看到。
- **减益做什么**：封印某类骰子（点数贡献归零但仍算牌型）、减少投掷 / 提交 / 容量、抬高目标、压制牌型或颜色倍率、让附魔 / 成长 / 部分控制器失效、扣金币。
- **应对手段**：调整控制器顺序与构筑；道具“破咒符”、控制器“替罪羊”直接解除；服务“贿赂首领”花钱重抽。
- **战利品**（首领关后商店里免费领）：稀有控制器三选一、附魔控制器三选一、牌型直接 +2 级、三项骰面改造、特制骰子三选一、三个道具；也可以整组折现 5 金币。

## 7. 界面与表现

- **界面全部由代码搭建**（`GameApp` 的各个 partial 文件 + `UiKit`），没有手摆的 UI 预制体；表现用的特效预制体由编辑器脚本生成。
- **主要画面**：主菜单、新建挑战、关卡选择、对局、得分明细抽屉、结算、商店、牌型手册（三页）、查看骰子（可拖动的立体骰子）、设置（显示、文字大小 100 / 125 / 150%、动画速度）、调试工作区。
- **先提交规则，后播演出**：每条命令先在规则核心里结算并存档，界面再按“回执”播放动画。演出有正常 / 快速 / 减弱 / 瞬时四档，跳过或切换不会改变结果。
- **已有的专属演出**：掷骰、锁定、计分逐项结算、高分提交的三档分数牌、达标印章、结算清单、商店进场与交易、骰面改造预览、附魔提示。
- **还没有专属演出的**：首领减益生效、战利品、骰面被卡牌永久改写、v0.9 / v1.0 的大部分新机制（它们沿用通用的计分节拍或只有文字）。
- **音频**：有基础的界面与计分音效、一条背景音乐；AudioMixer 总线没有接入。
- **新手引导**：首局跟随真实操作的引导条，可在设置里重开；另有独立的教学关。
- **键位**：R 投掷，L 确认锁定，Enter 提交，Backspace 清除待选，H 手册，Esc 暂停或关闭弹窗。

## 8. 工程结构

```
DicePrototype/                    Unity 工程
  Assets/Game/
    Core/Rules/                   纯 C# 规则：配置模型与校验、计分、控制器规则、概率、计分说明
    Core/Session/                 纯 C# 会话：一局的状态机、命令、商店、提交、结算、存档校验、调试场景
    Runtime/                      GameApp 入口、3D 骰桌、原子存档、显示设置、演出系统、验证与截图工具
    UI/                           GameApp 的界面 partial（按版本与画面分文件）、UiKit、对象池
    Editor/                       工程搭建与资源集成脚本、批处理测试入口、门禁构建
    Tests/EditMode|PlayMode/      NUnit 测试（EditMode 1920 项、PlayMode 201 项）
    Data/P0Config.json            全部内容与数值（生成文件）
    Data/GoldenScores*.json       三代黄金样例（160 + 260 + 446 条）
  Assets/Art/Art07*/              各版本的界面件、插画、图标、特效贴图
ArtSource/                        美术源文件、AI 生成的原图与记录、风格套件
docs/                             规格、任务、状态、流程文档
evidence/                         各版本的测试报告、构建凭证、截图、复核报告、模拟数据
tools/                            配置生成、黄金样例参考实现、交付与打包、美术管线、平衡模拟器
```

**分层原则**（三端长期意图的基础）：`Core` 不依赖 Unity 的画面、输入、文件系统，可以在普通 .NET 进程里编译运行——测试宿主、平衡模拟器都直接编译它。界面只读状态、发命令，不自己算规则；需要报价时向核心要（v1.0 复核后新增了一批这样的查询接口）。

**规则核心的几个关键文件：**

| 文件 | 职责 |
| --- | --- |
| `GameConfig.cs`、`ConfigJsonContract.cs`、`ConfigValidation.cs` | 配置的数据模型；逐字段的严格契约（多一个少一个字段都拒绝）；数值合法性校验 |
| `ScoreCalculator.cs` | 输入一份冻结的提交快照，输出得分与全部中间量、计分后计划（成长、骰面变更、扣款等）。无状态、无随机 |
| `ControllerRules.cs` | 技能来源解析（模仿、失效）、提交 / 投掷 / 容量预算、回收价、首领规则汇总 |
| `GameSession*.cs` | 命令式状态机：`NewRun / StartStage / Roll / ConfirmLocks / Reorder / Submit / EndStage / Continue / Buy / Sell / Study / UseItem / LeaveShop …`，每条命令原子执行、可重放 |
| `GameSession.Validation.cs` | 读档时对整份状态的合法性校验（防坏档、防手改） |
| `ScoreExplanation.cs` | 把一次计分还原成给玩家看的逐步说明，并自检与计分结果一致 |

**存档**：每条命令后原子写盘（临时文件 + 备份）；规则版本或存档结构不匹配的旧档不会被迁移，进入游戏时提示并保留原文件。调试工作区用独立的存档槽。

| 工具 | 作用 |

| `tools/art_v10/`（jobs、run_batch、stage） | 一个批次的任务表、串行批量生成、入库与清单 |
| `tools/unity_windowed_tests.ps1` | 在带窗口的编辑器里跑 PlayMode（批处理模式跑不了） |
| `tools/v10_delivery.py`、`package_v10.py`、`publish_v10_release.py` | 冻结身份 → 门禁 → 打包 → 发布预发行 |
| 两个 .NET 测试宿主（`Core/*/Validation~`） | 不开 Unity，几秒钟跑完规则与会话测试 |

**一个版本的标准流程**：规格与开发方案 → 配置生成器 → 规则核心 → 独立参考实现与黄金样例 → EditMode 测试 → 界面与 PlayMode 测试 → 模拟器升级与平衡 → 独立只读复核 → 冻结源码 → 测试发现清单 → EditMode → PlayMode 1080p → PlayMode 720p → PDB 核对 → 门禁 → 门禁构建（两平台）→ 打包 → 新目录解压回放取证 → 推送与预发行 → 更新 STATE。

**质量约定**（完整版在 [AGENTS.md](../AGENTS.md) 与 [QUALITY_GATES](QUALITY_GATES.md)）：证据必须真实并绑定源版本；不删测试、不降阈值，钉住旧数值的断言逐条改写并登记；失败与作废的轮次全部保留记录；实施者不签署最终验收，体验与美术由人判定。

## 11. 现状评估、已知问题与待定事项

**做得扎实的**：规则核心有三重保障（1920 项 EditMode 测试、与独立参考实现的 866 条逐字段对拍、与模拟器 30 万次随机对拍）；整局确定性与存档健壮性经过大量随机游玩验证；交付链条可复现。

**明确的短板：**

1. **没有真人试玩数据。** 难度、节奏、可读性、好玩与否的判断都来自机器人；机器人不会定向养成、不打单骰与顺子。
2. **新机制缺演出与音效**：首领减益、战利品、骰面永久改写、成长、再计一次。
3. **界面密度高、文字多**：卡牌说明是规则原文，新手门槛高；对局中的首领减益说明框很小；64 px 以下的插画图标有锯齿。
4. **平衡与体验上的已知情况**（2026-11-16 实测，详见 [实测报告](specs/v10/PLAYTEST_REPORT.md)；逐卡分析见 [强度与体验分析](specs/v10/BALANCE_REPORT.md)）：
   - 机器人 900 局通关 26.9%；会为首领做准备的机器人在同一批 300 个种子上 36.3%（发布时的机器人 29.3%）。前五个四关段平稳，最后一段陡（走进最后四关的局有三分之一死在这里）。
   - 一关通常一到两手结束，机器人估算的“实力 ÷ 目标”从 2.7 倍涨到 6.1 倍：构筑成长快于目标，后期的难度主要来自首领减益。
   - 减益强弱悬殊：缴械、凡人、万籁俱寂三个“让控制器失效”的减益是离群值。缴械可以靠调序化解但游戏没有教；凡人与位置无关；万籁俱寂基本只能靠取消或重抽。发布时的机器人低估了这三个减益，它的数据对它们偏悲观。
   - 金币：前期紧；中期起存款停在吃满利息的水平，后期利息占进账的 40%–47%。后期仍在正常花钱（每店近 3 件），没有证据表明“无处花钱”；扣金币的减益在高存款下几乎不疼。
   - 卡牌：没有发现必拿或明显超模的卡；68 张卡机器人很少买，强弱未知（包括大部分骰面养成卡）。
   - 高压关：机器人“稳了才接”，接了以后 98% 过关；但 28% 的失败局结束在高压关。
   - 文案缺陷（未修）：对局界面有三处内部编号外露（`ITEM_…`、`C01`、`C53`），倍率显示成分数，商店左栏的下一关目标没有计入首领减益，槽位满时货架标“已满”但其实可以替换购买。
5. **平台**：macOS 从未真机运行；Windows 的帧时间与独占全屏专项自 v0.7 起未通过、未重测；构建带 Development Build 角标。
6. **美术**：风格样板与锚点尚未得到确认；v1.0 的 62 张插画有 18 张小偏差待定；另有一份 2026-11-15 的美术方向探索稿（`ArtSource/AIConcepts/2026-11-15-style-exploration/`，由另一个会话产出，待筛选）。

**已推迟的想法**（用户提过、没有做）：无尽模式；高压关的非金币奖励；商店的流派偏向；多语言；移动端。

待用户决定的具体事项列在 [STATE](STATE.md) 的 v1.0 一节。

**加一张控制器要动哪些地方：**

1. 规格里写清触发条件、数值、与其他规则的交互。
2. `tools/v10_config.py`（或新版本的生成器）的卡表加一行，生成配置。
3. `ConfigJsonContract.cs` 登记这张卡允许的参数字段；`ConfigValidation.cs` 加数值检查与编号范围。
4. 计分类：`ScoreCalculator.cs`（触发判定与效果）、`ScoreExplanation.cs`（说明）；需要时 `ControllerRules.cs`（成长、预算）。会话类（关卡开始 / 结算 / 商店生效）：`GameSession*.cs`。
5. 界面：卡面状态文字（`GameApp.Controllers.cs`、`GameApp.V10.cs`）与得分明细；说明文字直接取配置。
6. 请独立方按规格更新参考实现并重生成黄金样例；补 EditMode 测试；改模拟器的快速计分模型（`tools/balance_sim/Fast.cs`）并跑 `verify`。

**加一个首领减益**：优先用已有的效果代码组合（配置里加一行即可，计分与会话都按代码生效）；新效果代码要同时改计分器 / 会话、参考实现、模拟器与规格第 3 节。

**踩过的坑（都真实发生过）：**

- PlayMode 不能在批处理模式跑；全量一轮约 27 分钟。其中一条资源诊断用例要求 20 秒内编辑器窗口不失焦、没有鼠标键盘输入——有人在用这台机器时会失败。跑 PlayMode 时不要同时跑模拟器等重负载。
- 每次带窗口的编辑器运行之后，要把 `DicePrototype/Assets/Game/Fonts/DiceChineseFallback.asset` 用 git 还原（编辑器会改写动态字体缓存）。
- 文本框高度小于一行、又用了省略模式时，整行不渲染而且不报错。v1.0 因此两次在打包后才发现首领减益说明框看不见：**新界面除了断言文字内容，还要断言可见（不被遮挡、字形在框内），并且在冻结前看一遍打包版截图**。
- 测试通过反射调用了 `GameApp` 的几个私有方法（参数个数固定），不要给它们加可选参数。
- 门禁拒绝重名的测试用例：`[TestCase]` 的数组参数会打印成同名，改用逗号分隔的字符串。
- 同一个仓库可能有别的会话在工作：提交前看 `git log`，不要覆盖别人写的 STATE 小节或未跟踪的目录。
- 界面不要自己重算规则。v1.0 的独立复核发现两处界面自己算错了数（利息上限、拖动时的容量），现在都改成向核心查询。
