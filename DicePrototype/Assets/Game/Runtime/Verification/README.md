# P0 built-player verification

`PlayerVerification` is dormant unless the player is launched with **both** `--verify-p0 <trace>` and `--evidence-dir <directory>`. It is not an ordinary gameplay feature. The initializer runs before scene `Awake` and redirects saves into a fresh evidence subdirectory. It never deletes or replaces the user's persistent save.

Run a **visible, unminimized** rendered Windows player, without `-batchmode`, `-nographics` or a hidden process window. The user needs to see the actual test player; a hidden background-helper launch is unsuitable for this visual/performance acceptance run:

```powershell
& 'E:/agent_workspace/gpt/game2/builds/Windows/DiceCraft.exe' `
  -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 `
  --verify-p0 'E:/agent_workspace/gpt/game2/evidence/runs/normal-win.json' `
  --evidence-dir 'E:/agent_workspace/gpt/game2/evidence/runs/player' `
  -logFile 'E:/agent_workspace/gpt/game2/evidence/runs/player-console.log'
```

Adjust the executable path to the actual build. The root agent owns Unity compilation, build settings and execution. Enable Unity **Frame Timing Stats** in the build if GPU/CPU frame timings are needed; unsupported GPU timers or unavailable profiler markers remain explicitly unmeasured. Do not silently replace the complete performance acceptance condition with idle-only sampling.

The probe performs these separate checks:

1. Takes a 1080p main-menu screenshot, then replays the supplied normal trace through `GameApp.StartNew`, `GameApp.Send` and real `TogglePending` selection. Every result must match the trace's phase, sequence, stage, scores, gold and remaining budgets. Each command reloads the actual atomic save and compares it and the UI's rendered state to the committed state. It verifies that both imported animation clips are bound, samples each visible `RollPivot` around 0.32 and 0.45 seconds into the first ordinary roll, and requires actual motion. The second roll exercises the real zero-duration reduced-motion path; every third roll uses `SkipVisual`. After every normal roll it checks zero position, identity rotation and unit scale on `RollPivot`, and verifies the committed physical face normal points to world +Y. These are actual built-player transform checks, not Editor samples. `isDebug` must remain false throughout.
2. Writes the winning state and its save hash. Installs one separately saved `isDebug=true` stress fixture using the existing private session setter. The fixture has 7 permanent + 3 temporary dice, 7 filled submit slots, 10 controllers, 5 items and visible red/blue, smooth/rough, gold and glass layers. It gives the Debug hand 500 rolls so the prescribed capacity can stay stable. The seven locked dice include every glass die, so repeated rolls of the remaining three cannot break the population. This fixture is not normal-run evidence.
3. Operates the real UI and save path for 10 seconds of warmup and at least 180 measured seconds. Each second rolls, skips animation, reorders the seven locked dice, selects an unlocked die, and clears that selection. Preview calculation remains part of every real refresh. No state injection occurs inside the measured interval. Autosave and action logging remain active.
4. Saves raw per-frame CSV, profiler marker inventory and a report with frame intervals, CPU/render-thread, GPU, GC allocation/memory/collections and UI build marker timing/counts, whenever those metrics are exposed by the actual player. Unsupported values use JSON `null`. Every metric reports expected frames and valid sample coverage. CPU, GPU, GC allocation and UI build timing need at least 95% coverage to certify complete measurement; this conservative probe criterion prevents a few valid samples from masking interrupted capture and does not replace the specification's frame budget. Recorder interruption remains an explicit gap even when earlier samples exist. It verifies the normal save hash still matches after the separate Debug stress run.

The UI recorder is streamed per frame using a reused list and `CopyTo(..., reset: true)`, with an explicit restart if reset stopped it. The probe checks `IsRunning`, cleared count, buffer wrap and batch size. A healthy empty batch means zero UI rebuild calls; one aggregate frame sample is used once; stopped/wrapped or multi-frame batches are missing evidence. Warmup samples are explicitly cleared at the sampling boundary. It never treats a stale `LastValue` as a new UI rebuild, and the buffer no longer grows with the total run length.

GPU timing validation rejects only impossible API values: negative/non-finite time or a single GPU frame longer than the entire process lifetime. A merely slow frame (including one above 16.7 ms) remains valid data. Original GPU values and classifications are retained in `gpu_raw_ms` / `gpu_sample_status`; any impossible sample forces a measurement gap rather than being silently removed. The separate `GPU Frame Time` profiler counter is diagnostic comparison data, not a silent replacement for the primary measurement. Recognized swapchain/timestamp warnings during sampling also force a gap. Native logs may bypass the Unity callback and must still be reviewed.

The frame list starts empty. At the end of the 10-second warmup, the probe measures actual frames per second and allocates `max(60000, ceil(observedFPS × 180 × 2))` records once, before establishing the measured clock and GC baselines. The report records observed FPS, safety factor, capacity, record size and estimated observer payload bytes (excluding object headers and other profiler overhead). Any subsequent expansion is recorded and still forces a gap. This accommodates unexpectedly unthrottled drivers without hiding observer allocations. The duration, 95% coverage requirement and 16.7 ms frame budget are unchanged.

Each launch creates `player-<UTC>-<unique-id>/` containing `player-report.json`, `normal-replay.jsonl`, screenshots, normal/debug state snapshots, separate save directories, `performance-frames.csv` and `profiler-markers.tsv`. The report binds Unity version, build GUID, configuration/trace hashes, CPU/GPU/OS, resolution and quality settings. Bind the final build executable/source hashes externally as part of the project evidence manifest.

The current extension (`probeRevision: p0-player-preallocated-capture-4`, report schema 3) captures the first rolled Selecting screen, first shop and full Debug capacity screen at actual 1920×1080, 1280×720 and 2560×1440 window sizes. It calls `Screen.SetResolution` and waits for three consecutive frames with the requested actual `Screen.width`, `Screen.height` and window mode. A 12-second timeout fails the verification; resizing an image or claiming a clamped window is the requested resolution is not allowed. Each set restores actual 1920×1080 before continuing.

Before its first accepted image the probe deliberately transitions through 1280×720 and back to 1920×1080, then requires three consecutive frames with actual visible content. Every subsequent capture also validates its pixels. The blank-frame heuristic samples a 16-pixel grid and requires ≥10% non-black samples, ≥0.5% bright samples and ≥8 quantized colors. It rejects all-black output, a flat clear color or an isolated watermark; it is not a layout/readability judgment. Attempts have a 12-second deadline, including a watchdog for a stalled end-of-frame yield. Rejected PNG files are retained under distinct `-rejected-<attempt>` names, reported in `rejectedScreenshots`, and never overwritten by a later successful image. Valid warmup images and accepted images are classified separately in `screenshotDetails`.

Before pressure sampling it additionally captures all 10 dice in the unlocked pool at all three resolutions. This uses a disposable, explicitly Debug clone with a `MemorySaveStore`; only the clone's ordered locks and current-result lock flags are cleared. It issues no rules commands or save writes, then restores the original stress `GameSession` reference and checks that its serialized state and save contents are unchanged. These pool-layout images are separate from both the normal run and the 7-locked/3-unlocked pressure measurement.

At each of those three resolutions, the probe also opens the existing `ShowDie` modal for normal and layered Debug dice (including the permanent-data 3D preview), then closes it through `CloseModal`. It opens the real `ShowBreakdown` modal after the first confirmed normal selection and for the full Debug hand, capturing the top, middle (normalized position 0.5) and bottom of its real scroll view. It verifies that the session, pending selection and save file are unchanged by these inspections. These captures and window changes occur before warmup/sampling. Stage settlement and final `RunWon` screenshots are retained.

`screenshotDetails` records actual dimensions, pixel-content statistics, acceptance/rejection, gameplay phase, command sequence, Debug status, focus and modal state per image. `animationChecks` records sampled TRS, sample times, motion deltas and landing tolerances, including partial data if a check fails. `probeAssemblyMvid` and `probeRevision` distinguish this source/build revision from earlier evidence. Screenshots still need the root agent's image-by-image layout review.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Replay/stress completed, required sampled metrics have ≥95% coverage without capture interruption at 1080p, frame-interval P95 ≤ 16.7 ms. Independent acceptance still required. |
| 1 | Exception, rejected command, trace/state mismatch, Unity error or incomplete functional check. Failure report contains the step and reason. |
| 2 | Replay/stress completed within the frame budget, but required metrics or 1080p verification are missing. This is incomplete performance evidence. |
| 3 | Replay/stress completed but measured frame-interval P95 exceeds 16.7 ms. Raw evidence is retained for optimization. |

The small `Validation~/ProbeCompile.csproj` compiles the component against the already-built project assemblies and locally installed Unity 6000.6.7f1 modules. Its executable runs 18 managed checks for percentile calculation, null metrics, sparse coverage, the 95% boundary, interruption reporting, JSON escaping, impossible GPU values, blank/visible image pixels and warmup-based buffer capacity. These checks invoke managed helpers only; they never construct a GameObject or call a Unity native API. This is a syntax/API and report-calculation check, not a Unity runtime or performance test. Its local paths can be adjusted for another machine. `Validation~` is ignored by Unity. Actual local results are in `compile.log` and `metric-checks.log`.

`GPU Frame Time` is a real Unity counter but represents the same Frame Timing Manager measurement as `FrameTiming.gpuFrameTime`; it is not an independent GPU instrument. Agreement is useful for diagnosing units and retrieval, while replacing missing API samples with zero-valued counter samples would falsely inflate coverage. See Unity's [6000.6 counter reference](https://docs.unity.com/en-us/engine/6000.6/manual/analysis/graphics-performance-profiling/profile-rendering/frame-timing-manager/counter-reference). The reported units follow the actual recorder descriptor (nanoseconds) and API result (milliseconds).

This is automated playback, not human playtesting, a win-rate estimate, or mobile validation. Screenshots require independent visual inspection; their existence alone does not certify readability or art quality.
