# 游戏开发质量门禁

本框架用于把人工策划转成可检验的任务与交付。目标平台包括 PC、iOS、Android；玩法、引擎、设备档位与品质预算仍为 TBD。

门禁由执行规范、少量本地确定性检查和后续引擎验证共同组成。目前已有来源、文件快照与 NUnit 报告检查工具，见 tools/QUALITY_CHECK.md；尚未接入引擎运行、CI、仓库权限或自动放行机制。文档和更多 agent 能提高约束与复核能力，不能保证游戏一定好玩。

## 决策权与验收权

- 用户决定玩法、创意、美术方向、体验目标、范围和品质取舍。
- AI 可以拆解已确认需求、执行制作、选择范围内的工程方法、验证与提出修改建议。
- 实施者提交产物与证据，不能自行把自己的任务标为 ACCEPTED。
- 独立技术复核者可以接受符合已确认标准的普通工程任务；用户验收核心体验、美术标杆与阶段升阶。
- 同一 agent 更换角色名称不构成独立复核。独立 agent 仍可能有共同盲点，不能替代真实游玩。
- 例外、降低质量阈值、删除已承诺内容或跳过必要验收，必须有真实用户授权记录；AI 不得代填授权。
- 正常实现、修复与已授权范围内的工具操作持续进行，不为每个小决定增加审批。

## 任务状态

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| DRAFT | 输入、范围或验收条件尚未完整 | 补齐后进入 READY |
| READY | 本任务具备开工条件 | 分配写入所有权后进入 IMPLEMENTING |
| IMPLEMENTING | 制作或实现中 | 产物具备后进入 VERIFYING |
| VERIFYING | 实施者运行检查并整理证据 | 通过后提交 REVIEW；失败进入 REWORK |
| REVIEW | 独立复核或必要的人工体验验收 | 通过进入 ACCEPTED；发现问题进入 REWORK |
| ACCEPTED | 对指定版本与适用范围验收通过 | 受影响的变更使其重新进入 REVIEW 或 REWORK |
| REWORK | 有明确未满足的条件 | 修复后回到 VERIFYING |
| BLOCKED | 缺失必要输入、工具或外部条件 | 条件恢复后返回记录的原状态 |

任何活动状态遇到实际阻塞都可进入 BLOCKED。阻塞记录应说明缺什么、影响哪条条件、已尝试什么、谁能解除；阻塞不等于任务完成。

## 开工条件

进入 READY 前，任务至少应具备：

- 唯一任务编号和引用的策划、技术、美术规范版本。
- 玩家可观察的目标，范围内与范围外事项，禁止擅自改变的内容。
- 交付内容、数量、变体与文件清单，可编辑源文件要求、依赖和写入所有者。
- 适用的验收类别，每条条件的编号、方法、场景、阈值和证据要求。
- 目标平台与验证环境，以及本次不适用项的事先说明。
- 复核角色、涉及的人工决策点和失败处理方式。

TBD 可以留在后续阶段的资料中；影响当前任务目标或验收的 TBD 必须先解决。本任务准备齐全即可开始，不要求整款游戏的所有细节一次性冻结。

标准在实现前冻结到任务版本。工程实现可以迭代，验收条件不能在看到失败后被实施者悄悄改写。

质量优先不要求大量内容或长文档。正式交付先完成必要的规格、接口、实机样例与验证准备，再扩展同类内容，具体见 QUALITY_FIRST_WORKFLOW.md。探索任务只冻结验证问题与边界，不要求提前知道试验结果。

## 六类验收

| 类别 | 检查内容 | 有效证据 |
| --- | --- | --- |
| functional | 玩家操作、状态转换、边界行为、错误恢复符合已确认策划 | 自动测试、可复现步骤、构建中的实际操作记录 |
| visual | 游戏镜头中的轮廓、比例、材质、动画、光照与已确认标杆一致 | 引擎截图、连续录像、标杆对照与人工评语 |
| performance | 指定设备和场景下的帧时间、内存、加载与资源开销满足预算 | 原始性能采样、设备配置、图形设置和场景记录 |
| experience | 信息可读性、操作反馈、难度节奏与体验假设得到真实游玩支持 | 游玩观察、行为记录、问题清单和用户判断 |
| portability | PC、iOS、Android 上的输入、布局、生命周期和构建符合平台目标 | 平台构建、设备或明确标识的模拟环境测试记录 |
| source | 源文件可编辑，导出与导入可复现，依赖与资源来源可追溯 | 源文件、导出产物、导入设置、来源记录与复现结果 |

每个任务按风险确定适用类别。文本修正通常不需要全套设备测试；影响共享输入、渲染、存档或平台接口的变更必须覆盖其真实影响面。

数量按完整可用的交付单元核对；缺少依赖、仍为占位或未通过约定条件的内容不计作完成。变体不能用重复文件凑数。

未运行不能写为通过；模拟器结果不能冒充真机结果；离线渲染不能替代引擎最终画面。标记 N/A 必须有适用性理由，不能用它隐藏失败。

## PC 与移动端的标准

三端共用体验目标，但验收需要平台矩阵。以下字段在对应阶段开工前填写：

| 项目 | PC | iOS | Android |
| --- | --- | --- | --- |
| 最低设备与系统 | TBD | TBD | TBD |
| 参考测试设备 | TBD | TBD | TBD |
| 分辨率与画质档 | TBD | TBD | TBD |
| 主要输入方式 | TBD | TBD | TBD |
| 帧时间与内存预算 | TBD | TBD | TBD |
| 构建与安装验证方式 | TBD | TBD | TBD |

- 使用实际可运行的平台构建检验核心循环，不能只在编辑器中运行。
- 输入验收覆盖本项目承诺的键鼠、触控或控制器操作；不默认所有输入方式都在范围内。
- 移动布局检查约定的屏幕比例、安全区域、文字可读性和触控目标。
- 移动生命周期检查切后台、恢复、中断以及存档一致性；长时间运行按已定预算检查温升与性能变化。
- 性能证据必须固定设备、分辨率、画质、内容规模、采样时长与帧时间统计口径，不能只给平均 FPS。
- 未具备某平台验证条件时，记录缺口并限制验收结论，不把另一平台的结果推定为通过。

## 证据与版本绑定

每个验收包应绑定任务编号、规范版本、源代码提交、实际构建或资产哈希，以及执行日期。尚未提交的工作树必须记录对应差异，不能只引用旧提交。

证据清单至少包含：

- 被验证的条件编号与结果，明确通过、失败、未运行或不适用。
- 工具、引擎和相关依赖版本；设备、系统与运行设置。
- 实际执行命令或可复现步骤，原始日志和测试报告。
- 需要时提供可玩构建、固定视角截图、交互录像或性能采样。
- 已知缺陷、适用范围、复核身份和结论。

截图证明外观，不独自证明交互正确；自动测试证明覆盖到的行为，不证明乐趣。重要条件应由复核者重跑或实际操作，不能只阅读实施者摘要。

文件存在、字段齐全、哈希一致属于完整性检查，不能据此声称品质验收通过。报告内填写了 ACCEPTED 也不等于获得验收权。

复核分别判断规格符合性、制作质量和实际运行。未完成的评审层、工具失败、零项扫描或没有发现任何测试，都不能解释为通过。NUnit 报告需核对实际用例、失败和跳过、预期数量与必要测试名称，不能只看进程退出码或总计大于零。

需求、实现、依赖或资源改变后，识别受影响的条件并重验。未受影响的历史证据可复用，但必须记录复用理由；失效的证据保留为历史，不继续用于放行。

## 返工与缺陷处理

必须修复影响任务目标的构建失败、崩溃、数据损坏、关键功能不通或品质条件不满足的问题，不能用总分平均掩盖硬性失败。

一般外观或体验问题也要关联到具体条件和可复现观察。可以延期的缺陷必须符合已确认的阶段政策，并进入有责任人与解决阶段的清单。

- 修复后运行直接相关的检查，并回归受影响的系统。
- 同类问题反复出现时分析根因，调整方法、工具或任务粒度；保留失败证据。
- 无法达到标准时，说明缺口及可行方案，进入 REWORK 或 BLOCKED；不以“已经花了很多时间”作为接受理由。
- 不能删除失败测试、替换低压力场景、降低分辨率或缩小内容规模来伪造通过。
- 原型可用占位内容，但必须在阶段范围内标记，并维护替换清单；未完成替换的正式内容不能冒充最终产物。

## 多 agent 的文件所有权

独立模块可以并行，依赖链按顺序执行。角色数量不等于同时运行数量；协调者按当前工具的实际并发限制分批派工。

同一 Unity Editor 会话、同一场景或 Prefab、同一 Blender 源文件同时只有一名写入者。可文本序列化的文件仍可能产生语义冲突，不能假定自动合并安全。

每次派工记录文件范围、写入者、依赖与交接状态。审查者默认只读。异常退出后由协调者检查真实文件和未合并改动，再释放所有权，不能直接覆盖现场。

## 如何逐步落实成工具约束

1. 当前先用任务契约、版本记录和独立审查执行规范。
2. 工具链确定后，将可判定的格式、导入、编译、测试和构建要求变成可执行检查。
3. 使用独立的构建与验收运行结果；对关键分支配置与仓库能力相符的合并限制和权限。
4. 保留人工体验、美术和范围决策。自动系统只放行它能验证的条件。

低风险修改使用轻量差异复核和相关检查；高风险系统、正式美术样板与阶段交付使用完整证据包。流程的成本应与错误影响相称。
