## 0 结论

现在的文字大多是**写给规则引擎的**，不是写给玩家的：

- 卡牌说明直接照搬规格原文：“至少提交2颗且S.Count<K，提交后前两颗本次物理面原值+1”。
- 内部编号直接显示：ITEM_00012、D001、F01/F06、C01、“容量 K”。
- 倍率显示成分数：×702/5。
- 结算用会计用语：“奖励前余额 0 → 结算后余额 7”。
- 同一个概念有好几个名字：道具、消耗品、局内道具。

统计：

| 范围 | 有问题 | 总数 | 主要问题 |
| --- | --- | --- | --- |
| 内容文字 | 194 行 | 270 行 | 规格用语 171、太长 83 |
| 界面文字 | 310 行 | 1,510 条 | 规格用语 166、用词不一致 71、开发信息 61 |

另外发现几处文字本身就是错的（§5），不论是否采纳改写都应修。

方案分五层：

1. 先定**用语规范**（§2）；
2. 统一**数字格式**（§3）；
3. 按两个附录**逐条改写**；
4. 做两处**结构调整**（§4）：卡牌改成“短文加细则”，界面字符串集中管理；
5. 修正**文字错误**（§5）。

### 2.3 写法

- 卡面短文是一句“条件 → 效果”，不超过 28 个字；上限、叠加、时机等边界放在细则里。两者合起来必须等于原规则。
- 主语要清楚：“这颗骰子”“提交的蓝骰”，不用“该骰”“其”。
- 提示写玩家下一步要做什么，不写系统状态。
- 玩家画面不出现开发信息：内部编号、变量名、版本号、美术方案名、英文枚举、异常信息。

## 3 数字格式

| 项 | 规则 | 例 |
| --- | --- | --- |
| 倍率 | 一律小数，最多 2 位，去掉末尾的 0；除不尽的加“≈” | ×140.4、×3.9、≈×0.33 |
| 概率 | 1 位小数，同一界面精度一致 | 16.7% |
| 概率变化 | 写百分点并配一个例子 | +15%（如 50% → 65%） |
| 大数 | 四位以上加千分位逗号（金币目前没加）；15 位以上的写法**待决**（建议“约 1.23×10¹⁹”） | 1,000 |
| 符号 | “×”“+”紧贴数字；减号用全角“−” | ×3、+10、−1 |
| 区间 | 用“~” | 1~3点 |
| 空格 | 正文与卡面里，数字和量词之间不空格（3点、1颗）；大字标题与状态栏数值保留现有空格（第 1 关、5 / 8）；全游戏只用这两种情况 | — |

格式化集中到一个函数（现有的 `GameApp.cs` `Factor`，格式 `0.##`，可以扩展）。需要改的函数清单见 UI 附录 §3.1–§3.3。

## 4 结构调整

1. **卡牌改成“短文加细则”两个字段。** 在配置里为每个控制器、道具、服务、改造、减益、战利品增加 `shortText` 与 `details`（字段名待定）：
   - 卡面和紧凑提示显示短文；
   - 详情页显示两者。

   现在的 `description` 是规则原文，开发与测试还在用，可以保留，但不再给玩家看。内容附录已经为全部 229 条说明写好了两栏。
2. **界面字符串集中管理。** 现在 1,670 条界面中文分散在 41 个 C# 文件里，用词不一致主要就是这样产生的。建议分两步：

   第二步工作量大，可以排在后面。

## 5 已经确认的文字错误

下面这些不是写法问题，而是内容错了。由主 agent 读代码复核了前两条（第 2 条在设置列表里无条件绘制，同一列表的演出速度选项也确是英文），其余来自 UI 附录：

3. 指定升级的标题写“本店一次”，配置允许每店 2 次（`GameApp.Shop.cs:150`）。
