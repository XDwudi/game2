本稿是24关版本的完整实施基线，替代P0 v0.4。核心仍为投掷、不可逆锁定、组合计分和关间购买；本版接入40件骰子控制器、7件局内道具、4项局外道具与服务、7项骰子强化，共58项内容，以及12种可升级牌型。新增控制器附魔、达标后继续提交、牌型手册和双平台构建交付。

01 目标与交付范围
一句话玩法：在有限投掷中锁定值得保留的骰子，把点数、牌型、红组和控制器组合成分数；达标后决定保留提交次数换取金币，还是继续提交改造骰子。
面向个人或3人以内团队，使用AI辅助代码、数据、资产与测试。单人、鼠标优先，3D骰子配合2D界面和背景。完整Run为8章、每章3关，共24关、23次商店。时长设计目标为40至75分钟，尚待真人试玩测量；支持稳定操作后的自动保存，允许分次游玩。
本版应交付可打开的Unity工程、Windows与macOS可运行包、同版本配置、Blender源文件和导出资产、测试记录、构建清单、操作说明、已知问题与Git交付提交。联网、跨Run永久数值成长、付费系统、每日挑战、无尽模式及新增Boss禁用机制不在本版范围。新Run重置金币、骰组、控制器、附魔、库存、牌型等级和折扣；设置与历史成绩可保留。

05 骰池提交栏与控制器槽
每颗骰子拥有稳定dieId、创建序号及F01至F06六个物理faceId。永久骰全部参加每手，不设置抽袋或备选牌库。临时骰使用标准骰面，只在本关存在；即使被复制、成长、染色，也不会变成永久骰。
有效容量为K=clamp(5+C21的1+C22的2−C09的1,1,8)。单持C21为6、单持C22为7、两者同持为8、再持C09为7。购买第六颗骰时K仍为5；出售扩栏控制器时K下降，但不会删除骰子或牌型等级。局内不能买卖控制器，K在一关内固定；骰子损坏也不改变K。
已锁骰构成有序数组S，连续占用前n栏，不允许中间空洞。确认锁定按待选顺序追加；超过空栏数时整个命令拒绝，不部分锁入。玩家可交换已锁骰的顺序，但不可拖回骰池或移除成员。第一骰是S[0]；C20指容量第K栏，必须占满K，不是任意部分提交中的末尾骰。
少数派比较S.Count<K，与N无关。N=6、K=5、提交5颗不触发；N=4、K=5、提交4颗触发；N=8、K=4时也只能锁4颗。未提交骰不贡献点数、牌型或红组。
控制器实例记录definitionId和enchantmentId。合法装备需同时满足：不同definitionId；普通占槽数≤4；所有实例总数≤10。不占栏位附魔的卡仍显示在装备区、正常生效且计入10件上限。卖出不占栏位的卡只移除自己；换成占槽版本前按最终装备集合重新校验，不允许挤掉其他卡。
06 投掷与不可逆锁定
点击未锁骰进入待选，再次点击可以取消；只有“确认锁定”才形成不可逆锁定。待选非空时阻止投掷、提交、用道具、调序和结束本轮，先确认或清除待选。锁定后点按只显示详情，调序不解除锁定。
一手从HandReady开始，没有有效结果。Roll需剩掷>0、存在未锁存活骰、待选为空、没有表现忙碌。扣一次投掷后，按骰子创建序号处理：玻璃先判损坏、幸存骰抽物理面、遥控覆盖指定当前点数、最后检查C05。整次逻辑结果保存成功后才播放动画。
剩掷为0时仍可确认锁定、排序、使用合法加次数道具、提交。全部骰已锁时禁止空投；K已满但还有未锁骰时，仍允许继续投这些骰子，消耗预算和玻璃风险，不能把其结果加入已满的S。不可为简化界面而改变C05的合法触发窗口。
至少投过一次、S非空、剩余提交>0才可提交；提交包含全部已锁骰。允许单骰或不足K的提交。先冻结并完成计分，再扣1次、累计分、执行后置改造、锁存qualified，决定结束或准备新手。只有准备新手或结束关卡时才清理本手效果，不能提前清除红潮或剩掷。C07首次机会只与本关有效提交序号有关，空提交或无效点击不消耗它。
C05每手仅一次，只在有效Roll结束时剩掷恰为0、未锁存活骰数量为1或2才返还3；0颗不触发。确认锁定、预览、排序、读取存档都不检查。返还次数计入剩掷奖励，返还后直接提交合法。I07不重置C05使用标志。
本版58项没有普通解锁效果；仅保留标记Debug的开发测试入口。暂停、切后台、跳过动画和读档不能重掷或撤销锁定。临时视为红色、有效点数转化不等于解锁，仍可以影响已锁骰的计分视图。
07 分层计分与唯一公式
每颗骰子区分永久物理面、当前投掷结果、计分有效数据和点数贡献四层。先应用C12把当前奇数+1，再应用C03第一骰视红，最后I01把全手视红。除明确例外外，控制器条件、牌型和红组都读有效数据；C19读永久六面原值之和，C34/C35读永久面的数字。
逐骰贡献先取有效点数，加上适用的C10、C13、C17、C19、C20、C39，再乘该骰玻璃2倍及当前物理面黄金2倍。两者同时存在是该骰4倍。C20仅对占满K时末栏有效6的那颗骰加6；普通末栏6的贡献变12，黄金玻璃可使该贡献变48。
令P为逐骰贡献之和，L为剩余投掷，J为C27触发时的整手基础+5，E为本次触发的基础分附魔数量，Q为触发的倍率附魔数量。G是同点家族中强化后最高倍率，A是顺子倍率，C是颜色倍率，R是红组倍率，X是基础控制器整手倍率的乘积。



基础+5附魔和C27的整手加5没有归属某一颗骰，因此不再乘逐骰玻璃或黄金；它们参与后续M、R、X和倍率附魔。多个基础加分相加，多个×1.2相乘。只在全部乘区完成后向下取整一次，删除旧版最终+F的规则和数据字段。
M与R使用实际倍率×100整数；×1.2采用精确6/5。核心计算为BigInteger(B)*M100*R100*X*6^Q / (10000*5^Q)，最后转换checked Int64得分，禁止使用float或每张卡分别取整。界面可显示小数倍率，规则和存档只保存精确来源。计分采用BigInteger便于统一精确运算，并承接Debug或后续扩槽的更大中间量；当前正常四普通槽约束并不要求计分必然超出Int64。概率原始权重乘百万量化单位则确实可能超出Int64，也采用BigInteger。
触发集合由本次只读快照确定；同一控制器一次提交只进入一次。与多少骰子受益无关，C39让五颗蓝骰各+2，也只触发该卡一次附魔。C07、C15等后置效果满足条件时可以触发附魔，但永久修改仍在分数确定以后执行，不回算本次分数。
预览与实际提交调用同一个纯计分器。预览不抽随机数、不消耗道具、不染色、不成长、不复制、不发钱；只展示后置效果计划。玩家调整S顺序后可以改变位置条件，但不能通过预览积累永久收益。

其余31个ID按本次提交条件触发。C03第一颗本来已红也满足；C12要求至少一颗当前奇数发生视为转换；C24要求有红色有效1；C25至少有一颗有效红；C29存在至少4个连续有效数字；C36/C37满足数量和空栏即触发，即使永久值到边界不再变化；C38每次有效提交触发，即使第一物理面已蓝。
已持有某ID时，允许它的不同非空附魔版本进入新商店。只在该ID合法附魔中排除none和当前附魔，按剩余权重归一化；无候选则排除该ID。无槽、加分、倍率没有固定优劣顺序，界面称“替换”。例如已持有无附魔计分卡，替换附魔按12:6:2抽；已持有无槽计分卡，按6:2抽。已持有无槽存钱罐则没有其他合法附魔，不能生成同名替换。
替换为原子交易：新卡标价减旧卡回收1是净支出；先模拟移除旧卡并加入新卡，再检查金币、普通槽≤4及总件数≤10。失败时两卡、金币和商品状态全部不变。成功后旧实例移除、新实例与固定附魔加入、商品售罄。若玩家先单独卖掉旧卡，再买原报价，就按完整新价购买，不能再减一次回收款。

18 金币收益价格与预算
设G为实际结束关卡前的持有金币，W为普通5或风险8，U为剩余提交次数，pig为持有存钱罐的0或1。


新发的钱不参与同一次利息。qualified不发钱；只有手动结束或合法自动结束才结算一次。达标后每多提交一次，少拿1货币剩次奖励；超额分不换金币，永久改造是继续的主要收益之一。C04、I06带来的未用次数可以正常转成钱。
G=27、普通奖励、U=2，无存钱罐新余额36，有存钱罐38；G=100、U=2时分别112和117。首次商店通常有16至18货币，取决于首关用了3至1次提交。控制器无附魔基础价5至14，带附魔最高20，部分高价附魔卡可能需要存钱后购买；第一报价优先低基础价新ID，但不保证附魔后的总价≤8。
道具3至6、骰强2至5、新骰基础价6至12、牌型首升5至12。附魔溢价、不占槽价值和同名替换只回收1共同形成换卡成本。所有价格和目标都在配置中，界面不另写一套数字。
条件收支检查：假设全普通、每关第一次提交后立即结束、初始10且不消费，限息后第24关余额284；沿用无上限利息则681。首店花8买存钱罐、其后不消费时，限息最终375，无上限为2611。这些是满足假设后的收支路径，不是无装备实际能通24关的证明。

20 架构与可扩展边界
Core使用纯C#数据和函数，负责计分、牌型、触发、概率、容量与价格；Application负责命令、状态机、事务、随机流与存档；Presentation负责3D骰子、uGUI、动画和声音；Content负责配置、图标与本地化文本；Editor工具负责导入校验、资产生成和构建。
不得用Transform朝向、Shader颜色或物理碰撞反推规则。Roll先确定物理faceId和当前值，表现只转到指定面。ScriptableObject可保存只读定义，运行中的金币、骰面和实例必须深拷贝为独立状态，不写回资产。所有新增效果由稳定ID映射到明确处理器，避免在UI写判型或硬编码价格。
将逻辑与Unity引用分开，以便在EditMode对黄金输入、概率和事务进行测试。同一数据配置驱动正式运行、手册、商品详情、计分拆解与测试。后续新内容只能通过版本化配置和处理器进入，不由开发AI自行补未定义的解锁、刷新、付费或物理判点机制。

附魔供给需要按实际商店规则观察。仅在“69张报价都按固定12%独立抽无槽”的简化前提下，预期会看到8.28张无槽；真实规则还包含非提交卡、已持有ID的条件化、去重和购买限制，因此不能将这个数解释为每局能买到8张不同且有用的无槽卡。总件数10、普通占槽4及替换后的容量校验必须执行。

25 技术基线与工程约定
本版按用户明确提供的已安装环境制作：Unity 6.6（6000.6.x）与 Blender 5.2。首次实施时读取实际补丁与构建标识，再写入工程说明；本文件没有读取用户本机程序，也不代表两者之间已经完成兼容测试。官方已经发布 Unity 6.6 Supported release，以及 Blender 5.2 LTS；后者公开支持期至 2028 年 7 月。[U1][B1] 不为采用旧模板而自动更换版本。
Unity 使用 Universal 3D 工程、URP、uGUI、TextMeshPro 与 Input System。Unity 6.6 的官方 UI 对照仍将 uGUI 列为运行时推荐方案。[U2][U3] URP 与 uGUI 的具体包版本以该工程实际解析结果为准；Input System 官方 6000.6 页面列出 1.20.1，已有项目先核对锁文件和引用再决定是否调整。[U4] 记录 Application.unityVersion、ProjectVersion.txt、manifest.json 和 packages-lock.json，不得只写“Unity 6”。
同一活动场景保留一个 EventSystem，使用与 Input System 对应的 UI 输入模块。鼠标、数字键和操作快捷键汇入同一命令入口；输入框编辑、模态面板和动画阶段屏蔽不合法动作。UI 禁用仅负责提示，规则层仍复核目标、余额、次数、容量和效果权限，防止键盘绕过按钮状态。
规则定义、58 件内容和资产索引均使用版本化 JSON；DTO 使用明确字段、数组和稳定 ID，运行时再建立查找索引。JsonUtility 处理结构化 JSON，顶层数组应包入对象，普通 DTO 标注 Serializable，不能用任意动态 JSON 树替代合同。[U5] 导入后验证所有内容 ID 唯一、引用存在、数值合法、58 条均有名称与图标映射。显示层只消费规则提供的数据，不另写一套概率或计分逻辑。
画面继续采用 3D 骰子与 2D 界面，不制作角色和 3D 桌面环境。一台固定正交相机绘制骰子；2D 背景位于骰子后方，HUD 在 Overlay Canvas。背景不拦截点击，鼠标被交互 UI 消耗后不再拾取下方骰子。设计分辨率为 1920×1080，验收 1280×720、1920×1080、2560×1440；用 Canvas Scaler 与锚点调整，避免缩小到文字无法阅读。

目标选择界面明确区分选骰、选物理面和选点数。遥控骰子要求恰好 2 颗不同的未锁骰，每颗独立选择 1–6 点；未完成两个目标时不能确认。确认同时消耗道具与 1 次普通投掷，全部未锁骰照常参加；幸存目标抽到物理面后，只把该面本次显示点数覆盖为所选值。即使永久六面没有该点数也能选，颜色、纹理、金层与 faceId 保持来自真实抽到的面。UI提示玻璃可能先损坏、目标损坏不补选或退款，并在持有 C12 时展示所选点数到有效点数的变化。
永久 pipValue、当前 pip 覆盖及来源分开保存，详情同时显示“永久面值 → 当前值 → 有效值”；该骰下次实际参与重掷或进入新一手时清除当前覆盖，六面永久编辑预览始终保留真实值。骰面强化显示可旋转的 3D 预览和六面展开图，两者共享 faceId。取消目标选择不扣款、不消耗道具。临时骰有“本关”角标；加入骰子展示其六面、颜色、加入后的骰数，并明确标注“提交栏不变”，删除操作明确展示要移除的骰子身份及其强化，并说明基础提交容量保留。

29 结果动画与 Blender 交付流程
规则先完成投掷事务，产生骰面、损坏、次数和必要效果记录并保存，再播放表现。骰面选择、玻璃损坏和内容概率效果使用主规则随机流；动画、声音和碎片使用独立视觉随机源。跳过、切后台或读档恢复已确定结果，不重抽、不返还次数、不重复触发控制器。真实碰撞、摩擦和最终朝向都不决定规则结果。
Prefab 采用 DiceRoot → RollPivot → FaceOrientation → DiceVisual。DiceRoot 负责池/槽位置；RollPivot 播放 Blender 翻滚；FaceOrientation 指向结果面；末帧 RollPivot 回到局部零位置、单位旋转、缩放1。换结果前保留当前世界姿态，以父节点补偿后过渡，防止首帧跳面。正常投掷总时长0.90秒：衔接0.10、翻滚0.70、落定0.10；快模式0.15秒，跳过直接对齐。结束后停止曲线覆盖，最终朝向必须匹配真实结果 faceId，朝上面的点数渲染读取 current pip；遥控覆盖不能通过转到另一个永久同点面来伪造结果。
锁定反馈0.12秒、选择0.08秒、提交明细约0.25秒。染色、复制、损坏和入池反馈建议0.15–0.25秒，多个效果可按结算顺序快速合并；减少动态模式用图标和明细替代位移。损坏碎片不成为可拾取骰子；骰子在池与提交区只存在一个身份。永久改面同步刷新三维面、六面永久预览与说明；临时当前覆盖只刷新本次显示及对照，不能污染永久预览。有效点数/颜色以计分标记显示，不改物理面资产数据。
Blender 5.2 官方资料确认后台运行 Python 脚本，并在 FBX 手册中区分新导入器与 FBX Add-on/Legacy 导出路径。[B2][B3] 本次未直接读取本机导出操作符，不把旧版参数签名当作已经验证。首个脚本记录 bpy.app.version、version_string、version_cycle 和构建标识；文件版本号不能替代应用补丁号。[B4] 随后检查实际 FBX 导出操作符与其 RNA 参数；不支持所需参数时停止导出、说明差异，不静默改用另一版本。
导出预设目标为：只导出需要的 Mesh/Empty；单位与尺寸统一；Forward=−Z、Up=Y；导出法线与最终网格；动画烘焙采样每帧、关闭简化、按命名片段输出。参数名及可用项根据本机导出器确认，保留导出预设。动画制作前应用Rotation/Scale；不随意启用空间变换烘焙或在动画完成后应用变换。程序化/物理动画先转成可导出的关键帧。
Unity 6.6 导入端核对 Scale、Convert Units、Bake Axis Conversion、法线与层级；官方说明轴转换可以烘焙进几何/动画数据，分文件动画应保持一致层级。[U6] 骰子使用简单BoxCollider，不自动生成动态MeshCollider；需要Rigidbody时由脚本/动画控制，不运行动态掷骰判分。材质在Unity中明确重建，不能假定Blender节点会原样保留。先完成一颗六面骰、两段动画及所有外观层组合的端到端检查，再批量导出内容。

第一次达到目标后，不自动切换商店。展示稳定的“本关目标已达成”标记，并启用“结束本轮”按钮，辅助文字为“结算本关，保留剩余提交奖励”。按钮的动作名称为 EndStage，避免与 SubmitHand 混淆。旁边保留正常“投掷”按钮，用于继续已经创建的下一手；不额外调用一次新手初始化。提示继续提交将消耗一次潜在剩余提交奖励，但能够继续触发合法的永久改造；不承诺超额分数自动换钱。具体可继续状态、提交耗尽及骰子全损坏的裁定以主状态机为准。
EndStage 仅在qualified=true、remainingSubmissions>0的HandReady或Selecting稳定状态可执行；未达标时按钮禁用并显示原因。存在待锁选择时须先清除待选，忙碌时禁用。玩家已经开始下一手时，按钮辅助说明“本手未提交骰子不计分、不触发提交效果”；结束不额外扣提交，奖励按结束时剩余提交数计算。点击后由规则事务丢弃未提交手并结算，UI不能提前改数据。无剩余提交时自动结算，不要求再点结束。达标提示只在首次达标播放；读档不重复弹出动画，不再次发钱。结束时的奖励预览直接调用规则提供的同一计算结果，余额、利息、剩余提交奖励在真实结算后刷新一次。
第24关也保留“结束本轮”选择；本关最终结算后进入整局胜利页而非生成第25关或商店。胜利/失败页显示到达关数、构筑、牌型等级、永久骰面和复现种子。长局允许从每个稳定状态继续存档，菜单明确区分“继续本局”与“开始新局”。
33 控制器附魔的显示与资产合同
附魔是 ControllerInstance 的状态，不是控制器定义ID的新卡种。每个商店实例最多携带一种附魔。未持有该控制器ID时，先按无附魔80%、免槽12%、基础+5为6%、整手×1.2为2%抽样；若该卡不具备提交触发资格，抽到两种计分附魔时回退为无附魔，不重抽，因此实际为无附魔88%、免槽12%。对应9个ID为C01、C04、C05、C16、C21、C22、C23、C34、C35。已持有该ID时，同名替换仅从该卡允许的、非空且不同于当前附魔的候选中按剩余权重条件化抽样；候选为空则该ID不进替换商品池。类型、价格和显示在商店生成时固定并保存；开关商店、查看详情、加载存档不会重抽。名称、基础效果与附魔效果分成两行，鼠标悬停可看独立说明。控制器售出价格仍固定1，不因附魔而变化。

控制器栏同时显示“普通槽占用 a / 基础槽容量”和“持有 b / 10”。免槽控制器不增加可被其他普通卡永久占用的基础槽位。购入、售出或换卡预览显示两组数字的前后值；达到10件后，任何新增ID均不可购买；保持总件数的同名替换仍按最终状态校验，不因此禁用。同名控制器附魔版本支持商店原子替换，详情显示新卡标价、旧卡回收1货币、净补差、替换后的普通占槽及总持有件数；校验失败保留旧卡和金币，不能先卖后买。基础分与倍率附魔的触发由规则层给出 Boolean 与原因，不通过控制器图标是否亮起推断。每个控制器每次提交最多产生一次附魔计分事件；非提交触发的9个控制器按配置排除计分附魔，生成时执行上述回退规则；其余控制器也必须实际满足本次提交条件才触发计分附魔，不能以“装备了就触发”代替条件。

34 Windows与macOS构建和Git交付
本版每个可试玩版本同时交付Windows x86_64和macOS Universal（arm64+x86_64）两个包。Unity 6.6 仍提供这两种macOS架构，但官方已标记Intel支持将弃用；本版固定6.6以保留Universal，之后升级引擎时必须重新评估架构支持。[P1] Apple Silicon实机为必测平台；Universal的Intel部分需有独立验收记录，未在Intel实机测试时清楚标记“构建包含x86_64，运行未验证”，不写成“双架构实测通过”。
Windows与macOS共享玩法、内容ID、数值配置、序列化与随机算法。默认使用Mono后端完成本阶段快速迭代；Unity 6.6官方列出Windows x64及OSX x64/Arm64的Mono支持。[P2] 如果现有工程已经稳定使用IL2CPP，保留其后端并记录；IL2CPP需要目标平台的原生工具链，不能假设同一主机能直接交叉生成全部平台。[P3] 不把后端改变和本版玩法更新混为一次未经验证的升级。
工程保存两个真实的Build Profile资产：Assets/Settings/BuildProfiles/Windows_x64.asset和Assets/Settings/BuildProfiles/macOS_Universal.asset。两者引用同一组入口场景和内容配置，分别记录架构、图形API、后端、开发构建标志、压缩与日志选项。使用安装于本机的确切6000.6.x编辑器与匹配平台模块；缺模块时按实际检查结果补齐，不静默回退到其他引擎版本。
自动构建入口放入Editor程序集，方法建议为PrototypeBuild.BuildActiveProfile。启动进程时通过-activeBuildProfile选择平台，再使用BuildPipeline.BuildPlayer(BuildPlayerWithProfileOptions)构建当前Profile，读取BuildReport并在失败时返回非零退出码。官方指出运行脚本中请求与当前活动平台不符的目标并不可靠，因此两个平台用独立编辑器进程；同一工作目录不并发运行两个Unity编辑器。[P4] 若使用CI并行，使用隔离检出目录及独立Library缓存。
启动参数合同为：-batchmode -projectPath <绝对工程目录> -activeBuildProfile <工程内Profile路径> -executeMethod PrototypeBuild.BuildActiveProfile -logFile <绝对日志路径> -quit。工具执行时把路径作为独立参数传入，不把未经转义的路径拼接为Shell代码。构建脚本校验配置版本、内容数量和测试结果后，按平台输出到独立目录；Editor构建按钮必须调用同一入口，不能绕过验收步骤。
Windows压缩包包含完整Player输出目录，至少有exe、对应Data目录及Unity生成的运行库，不只上传exe。[P5] macOS包保留完整DicePrototype.app目录、Info.plist、Frameworks/Plugins、资源、符号链接和可执行位。Mac包在macOS上检查与封装，避免Windows文件系统抹掉权限；Unity也提醒从Windows生成macOS包时需要处理可执行标记。[P1] 使用系统ditto创建包含.app顶层目录的zip；Apple的公证工作流提供了此种封装方式。[P6]
Mac封装示例为/usr/bin/ditto -c -k --keepParent "DicePrototype.app" "DicePrototype-p0.5.0-macos-universal.zip"。封装后在全新目录解压再启动，检查.app目录结构、执行权限与实际CPU架构。不要只验证构建目录中的原始.app可运行。最终SHA-256对压缩包计算，任何签名、公证或重新压缩之后都必须重新生成哈希。
内部试玩包记录真实签名状态，例如Unity生成的临时签名、未公证；不得把它标成Developer ID已签名或已公证。对外分发流程需要实际证书与Apple账号能力，使用Developer ID、当前支持的notarytool以及stapler；公证成功后将票据附到.app，再重新压缩。Apple明确区分签名、公证与附票流程。[P6][P7] 凭据保存在系统钥匙串/CI密钥环境，不写入Git、构建日志或文档。没有可用凭据时，继续交付明确标识的内部试玩包和待执行步骤，不声称已经通过公证。
“同步上传Git”定义为同一版本的两个平台包、同一份manifest、变更日志和测试摘要进入同一个交付提交；两平台玩法源码均来自同一个已冻结的sourceCommit。构建不要求二进制字节一致，要求源码、配置和游戏规则结果一致。交付提交会晚于源码提交，manifest保存sourceCommit；避免让压缩包嵌入尚未生成的自身交付commit而产生循环。
建议仓库目录为Releases/p0.5.0/，包含DicePrototype-p0.5.0-win-x64.zip、DicePrototype-p0.5.0-macos-universal.zip、release-manifest.json、CHANGELOG.md、SMOKE_TEST.md。zip采用Git LFS追踪，.gitattributes一同提交；LFS在Git中保存指针、通过配套远程存储完整内容。[P8] 至少配置Releases/**/*.zip filter=lfs diff=lfs merge=lfs -text，不要把Unity的Library、Temp、Obj、Logs、导出中间目录或本地存档当成发布产物提交。大规模旧历史迁移不属于本版交付步骤。
忽略规则只覆盖缓存和未封装构建目录；交付目录Releases/必须可被Git追踪。以下规则放入仓库根.gitignore，保留项目已有其他规则；包含例外放在可能排除Releases或zip的宽泛规则之后，并逐项核验实际生效结果。[P9]

LFS配置与忽略配置是两回事：.gitattributes只决定已追踪文件的存储方式，不能让被忽略的zip自动进入提交。提交前用git check-ignore -v -- <交付路径>查出实际匹配规则；如输出为后置!例外，确认其确实重新包含。再用git add --dry-run -- <双包及清单路径>确认可暂存，实际暂存后由git ls-files --stage确认两个zip、manifest、报告及.gitattributes均被追踪。不得用强制添加整个工程代替修正交付目录规则。
上传前的真实验证包括：对最终zip计算SHA-256与字节数；检查git check-attr filter -- <两个zip路径>均返回lfs；git lfs fsck成功；查看当前提交中两个zip对应的Git对象是合法LFS指针，且本地完整zip不是指针文本。推送后从一个新目录检出该交付提交并执行git lfs pull，重新校验两zip的真实字节数和SHA-256，分别解压启动。只看到Git提交成功、只有指针文件或只在开发机原目录启动成功，均不满足完整交付。[P10]
上传前确认两个zip完整、版本一致、LFS对象可读。之后按仓库现有分支策略创建交付提交并推送该分支及其LFS对象，不强制推送、不覆盖其他人的提交、不将缺失LFS对象的指针当作完整上传。远程仓库地址、分支、访问权限与LFS服务使用实际项目配置；未提供时不虚构地址或声称上传成功。任一平台构建/验证失败时，仍保留成功包和日志，但本次“双平台完整交付”状态为未完成；修复后一起交付。远程Git不支持LFS或配额不足时，报告具体阻碍和已完成产物，不能悄悄丢弃一个平台包。
manifest至少包含：releaseVersion、sourceCommit、contentConfigVersion、contentConfigSha256、saveSchemaVersion、unityEditorVersion、blenderVersion、buildUtc、两个平台的platform、architecture、backend、profile、packagePath、sha256、byteSize、signingStatus、smokeStatus，以及goldenCaseSetSha256和规则复现摘要。本规格不提供任何伪造哈希、占位提交ID或预填“passed”的manifest示例。缺失的实测字段标记未执行/未知并说明原因，不能把空值当通过；正式发布清单必须填入工具实际读取/计算的值。源commit、配置哈希和用例集哈希须在两个包内的版本页与manifest一致。
