# 质量优先的前期制作与任务流程

本项目优先减少做错方向、规格歧义、工具不兼容和集成过晚造成的返工。每轮可以只完成一个很小的内容，但交付的品质、可编辑性和验证程度必须符合当轮约定。质量要求和内容数量分开管理，不用增加产量证明进度。

这一流程补充 [开发框架](FRAMEWORK.md) 与 [质量门禁](QUALITY_GATES.md)。下列检查是项目执行规则；是否已实现自动检查，应以实际脚本、运行记录和验收结果为准。

## 先形成当前任务所需的资料

准备顺序为：人工意图 → 当前范围 → 质量参照 → 系统交界 → 技术试验 → 验收方案 → 实施。只补齐本任务依赖的内容，不要求用户一次填写完整游戏的所有文档。

- 人工明确体验目标、重要取舍与不允许改变的内容；AI 将口头描述整理成待核对的规则。
- 对每个共享状态、数值或实体，记录权威来源和使用方，避免多个文档各自维护不同定义。
- 明确参考作品中具体采用与不采用的部分；核心视觉、手感和节奏用实际游戏条件下的样例校准。
- 未决定但影响本任务的事项先解决；未来功能的 TBD 保留为待办，不阻塞无关工作。
- 已有授权直接引用。工程细节、常规修复和已确认方向内的制作由 AI 自主完成。

## 实施前的准备度检查

使用 [准备度模板](../templates/PREFLIGHT.md)，检查以下问题：

| 检查面 | 开工前需要知道什么 | 常见返工来源 |
| --- | --- | --- |
| 设计 | 输入、状态、边界、失败与恢复的结果 | AI 用游戏惯例补全了用户未决定的规则 |
| 依赖 | 接口、数据所有者、资源和任务版本 | 两个模块都认为自己负责修改同一状态 |
| 品质 | 对标样例、允许差异和评审维度 | 做完后才发现比例、手感或风格偏离 |
| 工具 | 版本、真实读写、导入导出和运行能力 | 生成了源文件，却无法在引擎中使用 |
| 验收 | 场景、阈值、设备、方法、证据和复核者 | 实现完成后才为其发明容易通过的标准 |
| 范围 | 当前可写路径、数量、非目标和占位政策 | 同时扩大内容和修改无关基础设施 |

准备度结论采用 READY、NEEDS WORK、BLOCKED 或 NOT ASSESSED。NEEDS WORK 是资料或方案需要修订；NOT ASSESSED 是检查未能执行，都不能作为 READY。该结论不是新的任务状态；任务状态仍按 QUALITY_GATES.md 记录。

## 先走查系统交界

选择最可能出现冲突的玩家场景，沿实际顺序列出触发事件、系统调用、数据读写、状态变化、玩家反馈及失败恢复。重点检查死亡与奖励同时发生、暂停与存档重叠、输入中断、界面关闭后异步结果返回等适用情况。

对每个场景回答：谁拥有状态，顺序是否确定，失败如何处理，玩家实际看见什么，PC 与触控操作是否表达同一意图。发现矛盾时引用两处具体规则，不靠多数 agent 投票决定设计。

文档走查用于提前发现问题，不能替代运行验证。将高风险场景转成后续测试或真人操作步骤。

## 两类实验分别管理

| 类型 | 目的 | 代码与资产的去向 |
| --- | --- | --- |
| 抛弃式实验 | 用最低必要成本回答一个不确定问题 | 与生产隔离；保留结论与证据，默认不作为生产依赖 |
| 可演进样板 | 验证生产方案、结构或资产管线，计划继续使用 | 从开始就满足适用的源文件、接口和测试要求；通过审查后可以演进 |

使用 [技术试验模板](../templates/TECHNICAL_SPIKE.md)，先确定问题、两种可能结果及其决策影响。试验范围和检查点按风险设定，不固定所有原型必须几天完成，也不因固定失败次数自动否决创意。

临时硬编码或占位若只用于抛弃式实验，必须标记；不能直接进入生产。可演进样板也不能仅因“已经写过”就免除审查。出现重复失败时根据新证据调整方法，保留有效成果并分析根因。

## 先做实物黄金样例

一类资源或交互开始扩展前，先完成有代表性的样例，使用 [黄金样例模板](../templates/GOLDEN_SAMPLE.md)。样例需要经过实际专业软件制作、源文件重开、导出、引擎集成和适用设备验证。

3D 样例按需要涵盖模型、UV、材质、动画、碰撞和 LOD；2D 样例按需要涵盖源稿、透明度、动画、切片、图集与过滤。步骤由制作路线决定。最终检查使用真实游戏镜头、光照、运动和输入，展示图不能代替运行效果。

样例同时固化质量标准和制作方法：哪些特征必须一致、哪些允许变化、导出导入参数是什么、哪里必须人工检查。以另一个有代表性的变体验证可重复性后，再扩大同类制作。

样例只对已验证的平台、设备和场景有效。PC 样例不能自动证明 iOS 和 Android 合格；完整切片仍按既定三端矩阵验收。

## 规格符合与制作质量分别判断

| 结论 | 要回答的问题 | 验证方式 |
| --- | --- | --- |
| 规格符合 | 是否完成了已确认要求，范围和行为是否正确 | 逐条验收条件、测试、边界和平台检查 |
| 制作质量 | 在规格允许范围内，是否达到约定的完成度与体验标准 | 黄金样例对照、视觉和手感评审、实际使用与真人试玩 |

两项都需要结论。功能清单打勾后仍可能有生硬动画、反馈混乱或源文件不可维护的问题；这些问题应依据既定维度描述。没有事先定义的主观偏好先作为改进建议，不偷偷变成新的阻断条件。

正式制作中发现标准不完整时，先记录差距并补充决策；不得事后用较低标准迁就当前实现。体验和审美取舍由人决定，AI 的专业评审用于提供证据和选项。

## 少量在制与分段复核

- 协调者根据当前依赖和复核能力限制同时进行的工作，优先完成端到端任务，避免大量半成品排队。
- 独立研究、模块或资源可并行；同一场景、Prefab、.blend 和全局设置同时只有一个写入者。
- 正式制作前检查方向与规格；结构或灰模阶段检查比例和接口；集成后检查最终效果。每次检查只解决该阶段能回答的问题。
- 核心规则、存档、跨平台共享层、正式样例和阶段交付必须独立复核；低风险修正可合并做轻量差异复核。
- 任务已经具备明确输入时继续自主实施；涉及关键人工取舍时，提交可比较的实物或方案，不重复申请已有授权。

## 变更与证据失效

审查记录需要绑定需求、依赖、样例、工具配置和实现版本。任何相关输入变化都要分析受影响范围；受影响检查重新执行，未受影响证据注明复用理由。只给主文档加版本而不检查依赖变化，不足以保持结论有效。

集成者复核子 agent 的实际文件与执行结果，再安排适当回归；子 agent 报告“完成”只是待核验的交付声明。

## 用返工原因改进流程

记录首次验收通过情况、缺陷在哪个阶段发现、原因属于设计歧义、实现偏差、工具问题还是集成问题，以及修复是否再次引入问题。用于改进下一次的准备和检查，不设统一百分比目标来迫使验收放水。

重复缺陷应转成适用的规范、检查或样例说明。需求发生真实变化导致的重新制作单独记录，避免为了降低返工数字压制必要的设计迭代。

## 方法来源与适配

吸收 CCGS 的准备度审查、跨系统场景走查、规格分工和审查输入追踪；本项目保留人工创意权，移除逐文件审批与统一时间阈值，并补充实际软件制作和三端样例验收。[CCGS 固定版本](https://github.com/Donchitos/Claude-Code-Game-Studios/tree/05ad7c8a5b8aa2aa86bbd3439ae7cf7295cac418)
