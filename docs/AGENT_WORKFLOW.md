# 面向质量的 AI 执行与交接

本文件把多 agent 分工落实为任务输入、输出和判定规则。当前使用会话实际提供的委派工具，角色按需分时承担；没有安装 49 个 agent，也没有将上游 Claude 配置转换成可自动运行的 Codex 插件。

## 主协调者的执行顺序

1. 读取当前状态、任务和相关权威规格，确认用户最新决定。
2. 区分探索任务与正式交付；正式任务按 PREFLIGHT 准备，探索任务先明确要验证的问题。
3. 建立最小任务图。每个任务写清消费什么、产出什么、哪些文件可写、谁负责集成。
4. 给高风险假设安排最小试验；给新的资产类型或交互形式安排黄金样例。
5. 分派相互独立的任务。依赖尚未稳定的下游任务保持准备状态，不让多个 agent 同时猜测接口。
6. 收到交付后核对实际修改、产物和原始证据，再交独立复核。
7. 修复后逐条核对旧缺陷及新影响，最后由对应权限的人员作出结论。
8. 更新追溯、风险、当前状态及文件锁；下一会话从这些记录恢复。

## 按职责提供任务包

| 角色 | 提供的输入 | 必须返回的输出 | 权限边界 |
| --- | --- | --- | --- |
| 规格核查者 | 人工设计、当前需求、接口和场景 | 歧义、遗漏、矛盾与验证建议 | 不替人决定玩法，默认只读 |
| 技术或美术实施者 | 版本固定的任务包、样例、工具和可写路径 | 可编辑源文件、运行成果、自检与未解决问题 | 不改验收标准，不写他人资源 |
| 规格复核者 | 原始任务与实际产物，完整任务差异 | 缺项、额外实现、误解和逐条件结论 | 不只读实施者摘要，不为凑数提问题 |
| 制作质量复核者 | 产物、规范、真实运行和测试资料 | 结构、边界、视觉、性能及可维护性问题 | 不把另一 agent 的断言当运行证据 |
| 主协调者 | 所有交接与复核结果 | 集成结果、当前状态、升级到人工的问题 | 不代替人工批准风格、体验或降标 |

普通任务可由一名独立复核者给出规格与制作质量两个结论；高风险、跨专业或存在争议的任务再增加不同视角。独立是相对于实施者而言，不等于不同模型一定具有不同盲点。

## 交接包必须带的上下文

使用 [交接模板](../templates/HANDOFF.md)。包含任务原文、输入文件及版本、相关决策、参考样例、允许修改范围、消费和产出接口、依赖、验收方法及交付位置。只传相关资料，但不要遗漏会改变任务含义的上下文。

有 Git 时记录任务开始 BASE 和交付 HEAD，并审查整个任务跨度；不要默认 HEAD~1 就是完整变更。未提交内容同时记录差异或内容哈希。未建立 Git 的准备期使用文件快照，明确其局限。

上游示例的模型名称、工具名单和路径规则不自动适用。每次分派检查本会话的真实能力，不虚构后台 agent、软件连接或自动化。

## 共享事实和追溯

共享状态、重要数值、公式、资源 ID 和接口应有一个权威来源。只注册跨模块确实会共享或影响验收的事实，不把每个局部变量都放进注册表。

- 需求使用稳定的 REQ ID；变更更新版本，废弃保留记录，不回收旧 ID。
- 任务引用需求和相关技术决定；证据引用验收条件与被测版本。
- 来源文档记录真实内容；任务摘要保留引用，不复制多份数值再分别修改。
- [追溯表](../templates/TRACEABILITY.md) 连接需求、决定、任务、产物和验证。技术试验可以对应风险或平台要求，不必伪装成玩家功能。
- 变更发生后沿关联关系列出失效规格、下游任务和证据；重新判定受影响范围。低影响变化不要求重验整个游戏。

## 复核结论必须互斥

每个必要复核维度只能是通过、有缺陷、未完成或不适用。未运行、读不到文件、工具失败、空返回、零项扫描都属于未完成或明确失败，不能解释成“没有发现，所以通过”。不适用必须有任务范围依据。

一条可行动缺陷包含：对应要求、具体位置或场景、实际与期望差异、影响、复现证据和验证建议。作者对缺陷有异议时核对证据和需求，不用多数投票决定事实。

返工结果逐项标记已解决、未解决或经授权变更，并检查修复引入的影响。硬性失败保持 REWORK/BLOCKED，不因为达到固定轮数而改为完成。低风险建议可按已有政策进入后续清单，不等于降低本次硬性条件。

## 只在必要处使用自动检查

本轮 [quality_check.py](../tools/quality_check.py) 能校验固定来源副本、输入与产物快照、NUnit 报告计数和结果。它不启动引擎，不证明日志真实性，不认证审核人，也不决定游戏品质。

代码返回非零时，调用者必须保留失败状态。记录结果的文件也应绑定任务与运行环境。后续在 CI 中调用时使用受控运行产生的证据，并按仓库能力设置合并限制；当前还没有这些外部约束。

## 框架自身的验证

确定性检查用真实负例验证：旧哈希、缺文件、越界路径、空测试、失败或跳过测试、摘要和明细不一致必须被拒绝。提示词的结构审查不能替代这些运行测试。

实际 agent 行为还需要一次端到端样板试运行，验证它是否会遵守文件范围、报告未完成、在关键歧义处等待决定以及保留真实证据。当前完成情况见 [框架验证记录](FRAMEWORK_VALIDATION.md)。

方法来源包括 CCGS 的协调与准备度、BMad 的依赖和覆盖检查、Superpowers 的审查包与根因分析。已按人工设计权、质量优先和本地工具能力改编，原文及许可见 [参考资料](../references/README.md)。
