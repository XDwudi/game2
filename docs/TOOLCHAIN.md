# 专业工具与三端技术方案

技术路线目前未定。Unity 和 Blender 是候选组合；选型依据玩法、镜头、品质目标、移动端预算、可用设备与实际接通试验。优先选择能稳定产出并复现成果的工具，不按插件数量衡量专业程度。

## 工具职责与选择原则

| 工作 | 候选工具或入口 | 必须验证的结果 |
| --- | --- | --- |
| 游戏运行与集成 | Unity 或选定的游戏引擎 | 场景能运行、资源正确导入、目标平台能构建并启动 |
| 3D 制作 | Blender 与适合的建模、材质工具 | 源文件可编辑，导出后尺寸、方向、材质和动画正确 |
| 2D 制作 | 按像素、矢量或绘画路线选工具 | 图层、分辨率、透明度、动画和游戏内显示符合规格 |
| 概念探索 | AI 生图与人工参考整理 | 用作待评审候选，能转化成明确的风格规格 |
| 自动化操作 | 官方 CLI、Editor 脚本、已验证插件或 MCP | 输入输出明确，失败可识别，重跑不会破坏资源 |
| 验证 | 引擎测试工具、Profiler、设备日志、截图与人工操作 | 能核对功能、性能、视觉和体验的不同要求 |
| 版本与任务记录 | Git、适合的大文件系统和任务记录 | 可恢复到特定源版本，资产与代码引用一致 |

先用已接通的专业工具能力，缺少可靠接口时再用 UI 操作。MCP 或插件只是连接方式。不能因为可以调用一个工具就推定它能生成可用的生产级内容；也不能因为已有技能说明就声称本机软件已安装。

## 技术选型时先回答

1. 玩法是否要求复杂 3D、2D 像素、物理、多人或高密度模拟。
2. 镜头、画面目标和最低设备性能是否相容。
3. PC 指哪些操作系统，移动端何时进入开发与测试。
4. 引擎能否满足目标平台，所需插件和原生依赖是否都有相应平台支持。
5. 团队是否能取得源工程、日志、自动化入口和可重复构建。
6. iOS 构建环境、设备、签名及 Android 测试设备是否可用。

结论写入决策记录。不要在首个原型前建立与玩法无关的大型通用引擎、复杂框架或在线服务。

## 跨平台的基本架构边界

| 部分 | 需要保持的边界 | 典型验证 |
| --- | --- | --- |
| 核心规则 | 游戏状态与规则尽量不直接依赖设备按键、屏幕尺寸或文件路径 | 相同行为在不同输入设备下符合相同规则 |
| 输入 | 动作语义与键鼠、手柄、触控映射分离 | 触控可达性、手势冲突、输入丢失与切换 |
| UI 与镜头 | 布局与安全区、宽高比、可读性适配；允许移动端专门设计 | 真机屏幕与游戏镜头下能看清、能操作 |
| 存档 | 统一数据模型与版本，平台目录和写入方式通过适配访问 | 写入中断、恢复、损坏处理及版本迁移 |
| 生命周期 | 暂停、回前台、音频中断、系统回收与恢复有明确规则 | 不依赖一次正常退出事件才保存进度 |
| 渲染与资源 | 按平台设置材质、纹理、阴影、LOD 和质量档 | 性能变化不破坏玩法必需信息 |
| 平台服务 | 购买、账号、成就、通知等仅在需求成立时接入，并通过独立接口 | 平台特定实现不会侵入全部玩法代码 |

多端发布不自动等于跨端联机、云存档、账号互通或购买互通。这些是独立产品决策，需要另立任务。

如果选择 Unity，Input System 的 Actions 可将动作与具体设备控件分离；触控体验仍需单独设计。[输入动作文档](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.11/manual/Actions.html)

Unity 提供安全显示区域和平台相关持久化目录。重要 UI 应在安全区内，存档不能硬编码桌面路径。移动系统可能在挂起后回收应用，不能只在正常退出时保存。[安全区](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Screen-safeArea.html)、[持久化路径](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-persistentDataPath.html)、[退出回调限制](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.OnApplicationQuit.html)

## 构建与设备安排

| 平台 | 早期需要安排的能力 | 验收边界 |
| --- | --- | --- |
| PC | 目标操作系统、干净环境构建、启动与输入检查 | 不将一个 PC 系统的通过推广到所有系统 |
| iOS | 支持的构建主机或云构建、Xcode 流程、签名及真机部署条件 | 导出 Xcode 工程不等于设备运行成功 |
| Android | 匹配引擎的 Android 构建支持及 SDK、NDK、JDK，设备部署与日志 | 模拟器与开发机结果不替代真机性能 |

若选择 Unity，iOS 流程先生成 Xcode 工程，再由 Xcode 构建应用；本地最终构建需要 macOS，也可评估官方云构建。Windows 工作目录本身不具备完整本地 iOS 构建链。[Unity iOS 构建流程](https://docs.unity.com/en-us/engine/6000.6/manual/platform-specific/iphone/ios-building-and-delivering/build-process)

Unity 的 Android 开发依赖对应的构建支持、SDK、NDK 和 JDK，并支持真机部署与日志诊断。[环境设置](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/android/getting-started/sdksetup)、[设备调试](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/android/developing/testing-and-debugging/debugging-on-an-android-device)

具体版本兼容、商店提交规则和签名要求，在选择工具及准备发布时按当时官方说明核查；本框架不预填可能过期的版本号和平台阈值。

## 接通试验

正式制作前用一个小型、可删除的测试资产走通整个路径。按选定路线执行，不强制 2D 项目进行 3D 建模。

1. 读取工具版本、项目路径和依赖，记录实际入口。
2. 建立或载入源文件，保存并重新打开，确认可继续编辑。
3. 3D 使用已知尺寸、方向标识和材质的测试模型；2D 使用已知像素尺寸、透明区域、枢轴和少量动画帧的测试资源。
4. 导出、导入引擎，检查尺寸、方向、法线、UV、材质、透明度、动画等适用项。
5. 放进实际测试场景，运行交互，再构建到计划平台并启动。
6. 保存命令、日志、产物、截图及设备结果；故意给出缺失输入等错误，确认工具能报告失败。
7. 重跑并重新导入，确认不会生成重复资源、损坏引用或遗漏源文件。
8. 从干净副本复现，或记录尚不能复现的具体原因。

“连通”至少需要实际读写、保存、重开和一个完整输出。“制作管线通过”还需要导入、构建、运行与复现。两者不能混写。

## 版本与文件规则

- 选定后记录引擎精确版本、渲染管线、包锁文件、建模工具版本、导出格式和配置、构建工具链与平台依赖。
- 升级独立成任务，用代表场景与三端构建验证影响后再采用。
- 源美术与引擎使用的导出件明确区分。不要同时修改两份再猜哪份是真实来源。
- Unity 资源与对应 .meta 一起管理，保留 GUID 引用。场景、Prefab 和全局设置由协调者分配单一写入者。[资源元数据](https://docs.unity3d.com/6000.0/Documentation/Manual/AssetMetadata.html)
- Unity 的同一工程不能被编辑器和另一个批处理实例同时打开；自动化按工程路径串行调度或使用独立副本。[命令行说明](https://docs.unity.com/en-us/engine/6000.5/manual/unity-editor/command-line-arguments/editor)
- 大型二进制资源需要明确的锁与版本存储，不能依赖文本自动合并恢复 .blend 内容。

## 逐步实现自动检查

第一层检查文件与资源完整性：命名、引用、元数据、导入错误、缺失纹理、适用的几何或内存预算。

第二层检查行为与构建：编译、关键规则、状态边界、输入、存档和核心流程，然后执行目标平台构建。检查测试确实被发现并执行；零测试、失败或异常跳过不能当作通过。Unity Test Framework 可输出测试结果供核查。[测试命令行](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html)

第三层检查真实运行：在目标设备固定场景、分辨率、画质、采样时长和热状态，记录帧时间分布、峰值内存、加载及关键卡顿。编辑器性能用于诊断，目标设备构建用于平台验收。[目标设备性能采集](https://docs.unity3d.com/6000.0/Documentation/Manual/profiling-target-device.html)

自动结果与人工视觉、体验结论共同形成证据包。配置 CI 时让运行结果来自实际构建与测试，并按仓库能力设置独立复核和合并规则；不能只读取实施者填写的“通过”。

当前已有 [本地检查器](../tools/QUALITY_CHECK.md)，可以严格核对给定 NUnit 报告和已声明文件快照。它尚未负责启动引擎测试或采集设备结果；将来接入运行器时必须同时保留原始进程输出、设备与版本信息，并验证失败确实传播到调用者。

## 工具能力登记模板

每个实际使用的工具登记：名称、用途、来源、精确版本、安装状态、连接状态、验证日期、调用方式、输入输出、日志位置、失败表现、可重跑条件、已验证平台和负责人。状态采用未验证、通过或失败。

Blender 可作为脚本化制作候选；具体 Python 和命令行参数应按选定版本核对并实机试验。后续文档入口：[Blender 命令行](https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html)、[Blender Python](https://docs.blender.org/api/main/info_tips_and_tricks.html)。当前未把其视为已接通能力。
