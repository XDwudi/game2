本稿是首个完整可玩原型的开发基线。游戏围绕投掷、不可逆锁定、组合计分和关间购买展开；一个Run包含六关，接入用户提供的20件骰子控制器、7件局内道具、4项局外道具与服务、7项骰子强化，并提供11种牌型强化。完成本稿对应内容后，即可进入原型试玩与调参。
Word用于阅读与评审；同版本Markdown额外包含完整JSON配置、计算参考、随机与事务合同、机器可读测试输入。二者采用同一规则来源。开发执行以Markdown及其嵌入配置为准，不混用v0.3的商店、目标分、倍率增量和槽位。本文没有宣称已经运行Unity构建或完成人类玩家平衡测试。
01 目标与交付范围
一句话玩法：在有限投掷中留下值得锁定的骰子，把同点、顺子、颜色、红组与装备效果组合成分数，超过本关目标，再用金币改变下一关的打法。
原型面向个人或3人以内团队，采用AI辅助代码、数据、资产与测试。第一构建为Windows 64位、单人、鼠标优先；这是制作默认，不预先决定正式发行平台。表现采用3D骰子与2D背景、界面、商店，不制作人物、剧情演出或3D场景探索。目标一局10至20分钟，实际时长在试玩中测量。
交付应包括可打开的Unity工程、可运行Windows构建、配置与存档说明、Blender源文件和导出资产、规则及流程测试结果、已知问题、操作说明和复现种子。首个原型不提供联网、跨Run永久数值成长、付费系统、每日挑战或无尽模式。新Run重置装备、骰组、牌型等级、道具折扣和钱；教程记录与设置可以保留。
02 已确认要求与本版执行解释
用户已确认：初始5骰；有限投掷与提交；锁定后通常不可解除；同点红骰取最大一组；顺子与全红等跨维度倍率相加；控制器、道具、骰强与牌型强化四类成长；每10金币产生1基础利息；控制器和未使用局内道具在商店卖出均为1金币；使用已安装的Unity 6.6和Blender 5.2。
以下是为消除附件歧义而确定的P0实现口径。它们是本版执行默认，不能被开发AI自行改成另一种含义。

05 骰池与有序提交栏
每颗骰子有稳定dieId和6个唯一faceId。永久骰始终参加每手，不设置抽袋或备选牌库。临时骰使用标准六面数据，只在本关存在；即使被复制或染色也不改变其临时身份。复制只复制可构筑属性，不复制身份、寿命或实例ID。
基础提交容量独立保存。加入永久骰使永久数量+1、基础容量+1至7；临时骰不增容量；删骰、玻璃损坏不减容量。有效K为基础容量减去简化提交的1，且至少1。本版正常基础容量从5起，因此装备简化提交时通常为4至6。一个手中K固定，不因损坏挤出已锁骰。
已锁骰构成有序数组S，按确认锁定时的待选顺序追加到前n栏。不能确认超过空栏数的待选，整个命令拒绝且不锁任何骰。已锁骰可通过交换或拖动重排该数组，所有骰仍连续占用前n栏；不能拖到骰池、删除成员或在中间留空。C03的第一骰是S[0]，C07的第二骰是S[1]，C15读前3颗，C20读实际容量第K栏且要求占满。
“少数派”比较S.Count与K，和N无关。例如N=6、K=5、提交5颗不触发；N=4、K=5、提交4颗会触发。简化提交使K=4时，提交4颗不触发少数派，提交3颗才触发。未提交骰无论当前点数多好，都不贡献计分或红组。
06 投掷与不可逆锁定
未选骰可以点选为待锁，再次点击取消；这只是临时选择。点击“确认锁定”才成为已锁，本手普通操作不可解除。已锁点击显示详情；重排仅改变顺序，不解除锁定。待锁集合非空时，投掷、提交、道具使用和调序均禁用；先确认或清除待锁。
一手开始为HandReady，没有有效结果。首次投掷后进入Selecting；已锁骰不参与以后投掷。投掷前先验证剩掷大于0、至少1颗未锁骰、待锁为空、无表现忙碌；扣1次后，对参与的玻璃骰先做损坏检查，再为幸存骰抽面、应用遥控当前点数覆盖，最后检查C05。逻辑结果写入后播放动画。
剩掷为0时仍允许选择、确认锁定、调序、使用合法补次数道具和提交。所有骰已锁时，禁止空投；提交栏已满但仍有未锁骰时，允许继续投掷这些骰子，界面显示“提交栏已满”；它们不能再锁入，继续投掷仍会消耗预算及承担玻璃风险。不得通过禁止这一合法状态与C05产生隐含规则差异。
至少投掷过一次、S非空且剩余提交大于0才可提交；空提交拒绝且不耗次数。1颗骰可提交。S必须包含全部已锁骰，不能临时隐藏不利成员。提交成功扣1次并累计分；未达标且仍有机会则进入新一手。
锁定不可逆限制的是骰子的投掷资格与成员关系，不禁止明确效果修改其计分视图。红色浪潮可以影响已锁骰，C03/C12也可以改变有效数据；它们不会重新掷骰。当前38项没有普通解锁道具，解锁只保留开发测试接口，必须有合法来源并把Run标为Debug。暂停、跳过、切后台与读档不重抽结果。
07 分层计分与唯一公式
为每颗提交骰区分四层：永久物理面数据 → 本次投掷的当前点数与颜色 → 本次计分的有效点数与颜色 → 该骰实际点数贡献。改贡献的+点或×2不参与牌型，也不改变红组的点数。
先应用C12：当前奇数+1成为有效偶数；随后C03把第一颗有效颜色视为红，I01再把全部有效颜色视为红。所有数字条件、牌型和红组统一读取有效点数；C19的“六面总和”是明确例外，读取骰子永久6面原值之和。
每颗骰子的点数贡献先取有效点数，加上适用的C10、C13、C17、C19，再乘玻璃2倍和当前物理面镀金2倍；两者同时存在为4倍。P为这些贡献之和，L为剩掷，G为满足条件的同点候选中当前倍率最高项，A为顺子倍率，C为颜色倍率，R为最大同点红组倍率，X为本次触发的整手控制器倍率乘积，F为C20的最终+6。


只有最后一次统一向下取整。无控制器及骰强时X=1、F=0，回到原始核心公式。C20的6分在所有乘区和向下取整之后加入；其他逐骰+点在乘区之前。多个整手控制器相乘，例如×2与×3组成×6；同名控制器不能重复装备。
所有M与R用倍率×100的整数。P、L、X、F为整数，核心计算为 (long)(P+3*L)*M100*R100*X/10000+F。使用checked检查，不允许溢出回绕；本版合法范围使用64位足够。没有匹配牌型时M=1，不额外叠加“散点1”到已有牌型上。
唯一顺序：验证 → 冻结有序提交快照 → 有效点数/颜色 → 逐骰贡献P → G/A/C与M → 红组R → 条件总乘X → 一次取整及F → 扣提交并累计分 → 应用复制/扩散的永久变更 → 判达标/失败 → 发一次奖励 → 清理到期效果并保存下一稳定态。后置永久变更不回溯改变本次分数，即使本次已经过关也正常保存到后续骰组。
预览与提交使用同一个纯计分器。预览不能推进随机数、消耗道具、复制骰、染色或发钱。后置效果预览只显示“提交后将发生”，实际命令以冻结快照构造一次性变更意图。

玻璃损坏。每次实际参加Roll的每颗玻璃骰独立做一次15%检查；锁定骰不检查。先损坏，再给幸存骰抽物理面；损坏永久移除实例和其全部强化，不给金币、不缩容量。下次投掷的损坏风险不是按手或按关结算。存活3次投掷的概率为0.85³≈61.4%，因此玻璃只定价2，适合愿意尽早锁定的风险打法。损坏提示与朝上面概率分开，不能把两者混成一个骰点概率。

新发放的钱不参与同一次利息。失败不发放当前关奖励；最终关也只发一次。I06或C04增加但未使用的提交可正常转化为每次1金币奖励，不能将同一个提交同时使用又计入剩余奖励。P0不设利息上限，保留用户每10金币给1的基础规则。

颜色同时用R/B或红/蓝文字标记；待锁与已锁用形状和锁图标，不只靠颜色。提供音量、减少动态、快动画与跳过结算表现。售卖、删除、玻璃风险和复制目标在玩家确认前具体可见；取消目标选择不造成损失。
20 规则架构与开发边界
使用不依赖Unity对象的C# Core：GameSession管理Run/关/手；RollService处理概率与抽面；HandEvaluator判型；ScoreCalculator返回纯明细；EffectService执行38个明确处理器；Shop/Economy处理交易与奖励；SaveService负责原子保存。DicePresenter和HUD只展示已接受的结果。
推荐目录Assets/Game/Core、Data、Runtime、UI、Art、Audio、Scenes、Editor、Tests。Bootstrap读取配置与存档，MainMenu管理新建/继续，Gameplay通过状态切换承载关卡、商店和结算。无需为每种卡创建场景。JSON为唯一数值来源，ScriptableObject如用于预览则从JSON生成，不维护第二份手抄倍率。
所有38项必须接入正式内容目录，不能留“以后补充”假按钮。每件内容有稳定ID、显示名、价格、参数、触发阶段、窗口/时效、合法目标、说明和图标ID。处理器显式注册；未知ID、缺少字段或非法范围使配置校验失败，不静默忽略。
Unity 6.6新项目可能默认不重载脚本域，初始化必须显式重置静态事件、缓存和单例；新Run重建数据，退出Play后再进入不能继承上一次Run。工程须通过连续进入Play两次的检查，不依赖域重载清理偶然正确。[U1]

购买、出售、随机改造把金币、库存/面修改、售罄、资格变化、RNG和回执一起保存；首次开店把生成商品与推进的随机状态同时保存。事务先在副本计算，写临时文件并原子替换成功后发布事件。写入失败冻结同一待提交快照，阻止后续规则动作，重试仅重写该快照，不再次抽数或计算收益。
使用Application.persistentDataPath的一份活动存档与一份有效备份。配置p0.4.0、结构2与旧版不兼容，旧Run不静默迁移；显示开始新挑战并保留旧成绩。Pending可在读档后清空，已锁顺序、持有道具、返还已用标记和所有随机结果必须保留。日志本地记录种子、动作、计分、效果、购买与余额，正常与Debug分开。

新效果使部分提交具有实际优势：K=5、少数派下，2蓝2蓝3蓝3蓝得60，加锁1红成为五颗反而得33。有限模型已允许部分提交和不可逆锁定，不能继续沿用v0.3“最后总是全交”的简化。
原型上线前仍需完成三类检查：规则黄金样例和状态事务自动化；在目标Unity版本中的可操作流程与资源导入；真人对规则、锁定风险与购买价值的理解。前三类必须分别写“已执行/未执行”，不能把脚本结果填成实机验收。
首轮安排5至8名未参与设计者，教程后独立玩至少2局。记录首关完成、失败关、每手决策时间、误锁与想解锁次数、卡牌购买与卖出、实际触发率、每金币带来的分数/可用次数变化、末关得分分布。重点观察C12过度压缩点数、C05节奏、简化提交与少数派、玻璃损毁、存钱罐滚利息及只堆加点的弱构筑。
调参优先顺序：先修规则与反馈，再修首两关和供给，再调价格/出现权重，再调后段目标，最后才考虑修改用户原始效果。若某路线弱，先核对它是否缺少乘区或实际触发条件；不为追求一样的胜率而把全部卡改成同质加分。每次变更配置版本，保留同种子对照。
25 技术基线与工程约定
本版按用户明确提供的已安装环境制作：Unity 6.6（6000.6.x）与 Blender 5.2。首次实施时读取实际补丁与构建标识，再写入工程说明；本文件没有读取用户本机程序，也不代表两者之间已经完成兼容测试。官方已经发布 Unity 6.6 Supported release，以及 Blender 5.2 LTS；后者公开支持期至 2028 年 7 月。[U1][B1] 不为采用旧模板而自动更换版本。
Unity 使用 Universal 3D 工程、URP、uGUI、TextMeshPro 与 Input System。Unity 6.6 的官方 UI 对照仍将 uGUI 列为运行时推荐方案。[U2][U3] URP 与 uGUI 的具体包版本以该工程实际解析结果为准；Input System 官方 6000.6 页面列出 1.20.1，已有项目先核对锁文件和引用再决定是否调整。[U4] 记录 Application.unityVersion、ProjectVersion.txt、manifest.json 和 packages-lock.json，不得只写“Unity 6”。
同一活动场景保留一个 EventSystem，使用与 Input System 对应的 UI 输入模块。鼠标、数字键和操作快捷键汇入同一命令入口；输入框编辑、模态面板和动画阶段屏蔽不合法动作。UI 禁用仅负责提示，规则层仍复核目标、余额、次数、容量和效果权限，防止键盘绕过按钮状态。
规则定义、38 件内容和资产索引均使用版本化 JSON；DTO 使用明确字段、数组和稳定 ID，运行时再建立查找索引。JsonUtility 处理结构化 JSON，顶层数组应包入对象，普通 DTO 标注 Serializable，不能用任意动态 JSON 树替代合同。[U5] 导入后验证所有内容 ID 唯一、引用存在、数值合法、38 条均有名称与图标映射。显示层只消费规则提供的数据，不另写一套概率或计分逻辑。
画面继续采用 3D 骰子与 2D 界面，不制作角色和 3D 桌面环境。一台固定正交相机绘制骰子；2D 背景位于骰子后方，HUD 在 Overlay Canvas。背景不拦截点击，鼠标被交互 UI 消耗后不再拾取下方骰子。设计分辨率为 1920×1080，验收 1280×720、1920×1080、2560×1440；用 Canvas Scaler 与锚点调整，避免缩小到文字无法阅读。
26 骰池提交槽与扩容界面
骰池、提交槽、控制器槽与道具槽是四组独立容器，不能共用“栏位”字段。初始正常骰数仍由主配置决定；本版骰池布局支持至 10 颗，提交槽支持至 7 格。购买永久骰同时使永久骰数与 baseSubmitCapacity 各加 1，基础容量最高 7；临时骰只增加骰池，不增加提交容量。删除或玻璃损坏不减少已经取得的基础提交容量；简化提交影响有效容量 K，不删除池中骰子。

目标选择界面明确区分选骰、选物理面和选点数。遥控骰子要求恰好 2 颗不同的未锁骰，每颗独立选择 1–6 点；未完成两个目标时不能确认。确认同时消耗道具与 1 次普通投掷，全部未锁骰照常参加；幸存目标抽到物理面后，只把该面本次显示点数覆盖为所选值。即使永久六面没有该点数也能选，颜色、纹理、金层与 faceId 保持来自真实抽到的面。UI提示玻璃可能先损坏、目标损坏不补选或退款，并在持有 C12 时展示所选点数到有效点数的变化。
永久 pipValue、当前 pip 覆盖及来源分开保存，详情同时显示“永久面值 → 当前值 → 有效值”；该骰下次实际参与重掷或进入新一手时清除当前覆盖，六面永久编辑预览始终保留真实值。骰面强化显示可旋转的 3D 预览和六面展开图，两者共享 faceId。取消目标选择不扣款、不消耗道具。临时骰有“本关”角标；加入骰子展示其六面、颜色及增加后的基础容量，删除操作明确展示要移除的骰子身份及其强化，并说明基础提交容量保留。

29 结果动画与 Blender 交付流程
规则先完成投掷事务，产生骰面、损坏、次数和必要效果记录并保存，再播放表现。骰面选择、玻璃损坏和内容概率效果使用主规则随机流；动画、声音和碎片使用独立视觉随机源。跳过、切后台或读档恢复已确定结果，不重抽、不返还次数、不重复触发控制器。真实碰撞、摩擦和最终朝向都不决定规则结果。
Prefab 采用 DiceRoot → RollPivot → FaceOrientation → DiceVisual。DiceRoot 负责池/槽位置；RollPivot 播放 Blender 翻滚；FaceOrientation 指向结果面；末帧 RollPivot 回到局部零位置、单位旋转、缩放1。换结果前保留当前世界姿态，以父节点补偿后过渡，防止首帧跳面。正常投掷总时长0.90秒：衔接0.10、翻滚0.70、落定0.10；快模式0.15秒，跳过直接对齐。结束后停止曲线覆盖，最终朝向必须匹配真实结果 faceId，朝上面的点数渲染读取 current pip；遥控覆盖不能通过转到另一个永久同点面来伪造结果。
锁定反馈0.12秒、选择0.08秒、提交明细约0.25秒。染色、复制、损坏和入池反馈建议0.15–0.25秒，多个效果可按结算顺序快速合并；减少动态模式用图标和明细替代位移。损坏碎片不成为可拾取骰子；骰子在池与提交区只存在一个身份。永久改面同步刷新三维面、六面永久预览与说明；临时当前覆盖只刷新本次显示及对照，不能污染永久预览。有效点数/颜色以计分标记显示，不改物理面资产数据。
Blender 5.2 官方资料确认后台运行 Python 脚本，并在 FBX 手册中区分新导入器与 FBX Add-on/Legacy 导出路径。[B2][B3] 本次未直接读取本机导出操作符，不把旧版参数签名当作已经验证。首个脚本记录 bpy.app.version、version_string、version_cycle 和构建标识；文件版本号不能替代应用补丁号。[B4] 随后检查实际 FBX 导出操作符与其 RNA 参数；不支持所需参数时停止导出、说明差异，不静默改用另一版本。
导出预设目标为：只导出需要的 Mesh/Empty；单位与尺寸统一；Forward=−Z、Up=Y；导出法线与最终网格；动画烘焙采样每帧、关闭简化、按命名片段输出。参数名及可用项根据本机导出器确认，保留导出预设。动画制作前应用Rotation/Scale；不随意启用空间变换烘焙或在动画完成后应用变换。程序化/物理动画先转成可导出的关键帧。
Unity 6.6 导入端核对 Scale、Convert Units、Bake Axis Conversion、法线与层级；官方说明轴转换可以烘焙进几何/动画数据，分文件动画应保持一致层级。[U6] 骰子使用简单BoxCollider，不自动生成动态MeshCollider；需要Rigidbody时由脚本/动画控制，不运行动态掷骰判分。材质在Unity中明确重建，不能假定Blender节点会原样保留。先完成一颗六面骰、两段动画及所有外观层组合的端到端检查，再批量导出内容。
