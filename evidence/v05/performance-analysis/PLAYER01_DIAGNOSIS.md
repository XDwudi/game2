# P0 v0.5 Player01 性能诊断

状态：**REWORK，原性能门槛未通过**。本诊断只读已有 Player CSV、报告和源码，没有重跑 Player、选择较好样本、修改生产文件、节拍器、采样、操作日程或16.7ms阈值。`analyze_player01.py` 可复现全部统计；原始文件哈希和被测源码 `7121336e6d5e9b36f22401f09d188ff7b6bcae0d` 的绑定在 `player01-v04-comparison.json`。

## 结论与证据

最值得先优化的是**保存事务重复读回、反序列化并全量验证旧 active 文件**。现有证据强烈指向随历史增长的事务成本；新增预览/界面固定分配进一步吃掉余量。数据没有调用栈级计时，不能把每个长帧精确归到 JSON、磁盘 flush、复制或 GC 的某一个函数；因此下面将观察与推断分开。

两版实际硬件/Unity相同；操作均为含预热190次Roll、190次Reorder、190次选择/清除，历史回执均从2条增长到382条。v0.5要求K8，旧版K7，控制器/附魔不同，因此这是保留实测的跨版本比较，不是假称控制变量完全相同的A/B实验。GC次数反而减少，不能把问题称作“GC次数变多”。Canvas.BuildBatch仅代表该marker，不包括所有TMP、布局和UI业务工作。

### 慢帧与事务对应

ProfilerRecorder的分配数描述已结束的上一帧；源码已有此采样语义。按CSV相邻行对齐，而非把同一行的0B错误解释成“慢帧没分配”：

- 每版都有359条单帧分配≥200KB记录，时间相位对应每秒的Roll/Reorder。其**前一条LateUpdate**均值从旧18.8610ms增至20.0918ms，P95从22.3523ms增至24.2513ms。
- v0.5全部157个>20ms帧均落在这359个事务执行行上；旧版105个>20ms帧也全部如此。v0.5最高5帧之后记录的分配分别约3.14–3.30MB。
- 非事务Refresh分配组每版542条（50KB–200KB）；v0.5对应前一条LateUpdate均值16.6687ms，**没有>20ms帧**。故减少这组工作有余量收益，事务路径更优先。
- 事务之外仍有298帧>16.7ms（旧173帧）。不能保证修一个热点就一定通过，修后须按原完整场景重新测量。

这里的分组仅用于归因诊断；最终通过/失败仍使用全部10,722帧的原指标，没有用子集替代验收。

### 随回执历史增长的成本

v0.5四个45秒区间均值为16.7040、16.7456、16.7992、16.9020ms；旧版也从16.6807增长到16.8170ms。

事务分配对事务序号的线性拟合：v0.5每增长一条事务约增加**8,283B**，R²=0.999726；旧版约8,196B，R²=0.999776。这与源码全历史复制、序列化、旧存档反序列化及验证的O(N)路径一致。新版本并未首次引入该路径，而是在其上增加固定工作。

源码链路：`GameSession.Execute` 克隆整个RunState → append receipt → ValidateState → `SavePending`再次克隆 → `AtomicSaveStore.Save`序列化整个快照、写临时文件并flush → `TryRead(old active)`重新读文件/JSON envelope/完整RunState/ValidateState → File.Replace → `GameApp.Refresh`再获取一份整个RunState的展示副本。没有删去回执或降低持久化标准的理由。

压力场景从未Submit，回执种类只有NewRun、StartStage、Roll、Reorder。其运行态lastSubmission为空；Unity写出的空占位由TryRead正规化为空。因此新加的**真实提交历史计分强校验并不是本次压力循环的主热点**，跳过它既不能针对根因，也会重新引入损坏历史读档缺陷。

### 可证实的新增固定开销

总分配增加39,337,377B（5.13%）。542次非事务Refresh组平均从55,830B增至84,145B（+28.3KB），该组总增15.35MB；359次事务组平均增66.8KB，总增23.99MB。事务分配增长斜率则只略升，支持“原有历史增长路径+新增固定工作”的判断。

v0.5每次ScorePanel都会重新FreezeSubmission和Evaluate，即使只是Busy/Skip或待选改变、提交骰和提交序号完全相同。Evaluate新增完整控制器触发集合、附魔实例合法性和多个LINQ扫描；逐骰说明对象仍在计分时构造，且C39等新增来源增加说明。该代码路径确定存在，但本CSV没有函数级分配标签，不能把全部28.3KB都归给某一个调用。

## 推荐修复与缓存边界

1. **优先优化AtomicSaveStore旧active验证的重复解析。** 对同一store最近一次已知有效、成功落盘的完整envelope bytes保留私有缓存；下次仍读取真实active全部bytes，逐字节完全匹配时可复用其“已验证有效”结论。首次、任何字节变化、版本变化都走原TryRead强校验；损坏原件保留和有效backup保护不变。不能以mtime/长度代替内容相等。
2. **“写入成功”不自动等于“内容合法”。** 当前Save公开入口本身不验证新snapshot，不能只因File.Replace成功就缓存为有效，否则其他直接调用Save(非法Run)会在下一次把坏active轮换覆盖好backup。缓存前必须证明新snapshot通过生产ValidateState，或提供等价可信的已验证入口；不要依赖无法由adapter自身保障的假设。
3. 缓存只在Move/Replace成功后更新；验证、IO、替换任何失败都保留原缓存，重试仍是原候选。不外露或复用可被调用者修改的byte[]。store配置须在生命周期内保持同一冻结身份；不能跨配置复用有效性。现有外部改动后回退、无先Load直接Save、损坏历史、版本隔离和写失败重试测试均应保留重验。
4. **次级优化：GameApp内部缓存预览。** 按Session对象身份和accepted actionSequence失效，Busy/待选纯展示刷新复用同一冻结预览。Roll、Reorder、购买/强化、提交、读档或替换Session必须失效；不要把可变缓存结果从Core公开API直接返回而破坏预览隔离测试。显示内容、实时预览和UI刷新仍保留。

暂不建议为这次故障更改概率/计分规则、删除历史、降低有效性检查、延迟/取消保存、关闭GC、修改pacer或换统计口径。下一轮只在修复后跑原完整Player验收，并比较事务分配斜率、全部帧P95和独立时钟，不筛选或隐藏本次失败。
