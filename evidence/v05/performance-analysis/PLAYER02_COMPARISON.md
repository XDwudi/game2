# Player02 与 Player01 独立性能复核

复核日期：2026-10-30。复核者：独立子 agent `/root/v05_play_fixtures`。范围：只读已保留的实际 Windows Player 记录和绑定源码；没有启动或重跑 Player，没有修改游戏、探针、原 CSV 或验收标准。

**规格符合性：Player02 通过 Windows 侧 V05-PERF 的原完整帧 P95 ≤ 16.7 ms 门槛。** 原始 CSV 重新计算得到 P95 16.6913 ms，与 Player 报告一致。Player01 的 16.7700 ms 失败记录仍完整保留。macOS 的实机门槛不在本次复核范围内，不能从本结果推定通过。

**制作质量：保存事务分配和长历史增长成本确实下降，变化与最近一次有效存档的逐字节缓存修复一致。** 长历史成本仍然存在，P95 的通过余量仅 0.0087 ms；本结果不表示每一帧都稳定 60 FPS，也不保证其他设备或更长运行中的相同表现。

- 本目录 `PLAYER02_COMPARISON.json` 保存逐文件 SHA-256、完整帧统计、原报告、同负载检查、原始慢帧及相邻 Profiler 记录、历史计数与回放对比。

完整帧统计严格复用原探针的规则：只排除启用采样时的第一个不完整间隔，保留随后所有完整帧，包括超过 180 秒边界的末帧。P95 使用原来的 nearest-rank 定义。事务分组和四段统计仅用于定位原因，不参与重新选择通过样本。

## 验收条件没有变化

对两个嵌入提交执行 `git show` 并逐字节 SHA-256 对比，以下 12 个文件均一致：`FramePacer.cs`、`PlayerVerification.cs`、`GameSession.cs`、`GameSession.Validation.cs`、`ScoreCalculator.cs`、`P0Config.json`、`GoldenScores.json`、质量设置、项目设置、Windows 构建配置及两个包清单。具体路径和哈希见 JSON。

实际报告中的 17 个负载/计时配置也完全一致：1920×1080、10 骰子、8 提交栏、10 控制器、5 道具；预热 10 秒后采样至少 180 秒；每秒 Roll、跳过动画、调整锁定顺序、选中与清空待确认项，真实自动保存和 UI 预览保持开启。含预热两次均执行 190 次 Roll、190 次 Reorder、190 组选中/清空。有效指标覆盖最低要求仍为 95%。

探针均为 `p05-player-independent-clocks-7`，原 `FrameBudgetMs=16.7`、`SampleSeconds=180`、LateUpdate 采样位置和第一不完整帧排除规则均未改变。两次的生产 FramePacer 前后均已安装，仍为实际释放点重锚定的 60 Hz 最大节奏、QPC/10 MHz、粗 Sleep 加最多 1.5 ms 自旋尾、失焦/暂停 Sleep(17 ms)、vSync=0、targetFrameRate=-1；没有改帧节奏器使数字通过。两次采样帧缓冲扩容、采样图形计时警告均为 0。

Runtime 程序集 MVID 确实变化，因为 `AtomicSaveStore` 与布局代码重编译；这不等于探针源码改变。上述提交内容哈希和实际报告版本共同绑定该结论。

## 事务与长历史变化

两次压力初态均有 2 条命令收据，终态均为 382 条；终态种类均为 NewRun×1、StartStage×1、Roll×190、Reorder×190。初/终状态 JSON 长度也分别相同（29,346 / 364,489 B），没有截短历史或减少工作量。

按既有诊断规则，托管分配 ≥ 200,000 B 的 359 行对应提交到持久化的事务操作。ProfilerRecorder 提供已完成帧数据，因此比较它们的前一 CSV 行 LateUpdate；相同偏移应用于两次全部记录。

增长斜率下降 **40.49%**；每次保存仍读取当前文件并完整校验候选、复制/序列化增长中的历史，所以斜率没有归零。两次全部 >20 ms 间隔分别为 157 和 106，均与事务大分配在上述一行偏移下对应。Player02 最慢帧在 155.9901093 秒、24.8720 ms，下一行记录 Main Thread 24.8448 ms 与分配 1,994,121 B。证据支持事务链是剩余峰值来源之一，但 CSV 没有单独计时每个存储方法，不能精确拆分 CPU、同步磁盘 I/O 与每次 GC 的贡献。

非事务刷新诊断组（50,000 至 200,000 B）的平均分配几乎未变：84,144.78 → 84,163.84 B，两个组均没有对齐的 >20 ms 间隔。全帧分配 P95 仍为 99,672 B，也表明重复 UI 预览的固定分配没有因本次修复消失。本次没有实现预览缓存，不能把改善归功于它。

源码差异与该观察一致：`AtomicSaveStore.Save` 先完整校验候选；对于原 active 文件，只有磁盘全部字节与本 store 最近一次成功提交的私有有效 envelope 字节相同，才避免再次 JSON 反序列化和历史校验；首次保存、外部变更或不相等仍走原完整 `TryRead`。缓存只在 `File.Replace/Move` 成功后更新。原校验源码、文件落盘和备份/损坏文件处理路径没有被删除。其他差异仅为手册/提示布局位置、增加两项缓存回归测试、构建门禁从 552 提高到 554 项 EditMode。

这是一台机器上两次保留运行的比较，并非多轮受控基准；还有一个小布局修正同时进入第二次构建，不能把每个时间差都精确归因到缓存。但相同历史长度、事务分配总量与增长斜率的大幅下降，以及非事务刷新组基本不变，对修复作用提供了比单看 P95 更直接的证据。

## 功能与剩余限制

两次配置、黄金集和正常轨迹哈希一致。正常回放 161 行与 Debug24 回放 178 行的全部游戏字段及逐步 `ruleStateSha256` 完全相同；只忽略随机生成的 `commandId`。两个正常回放都按既定轨迹在第 9 关 `RunFailed`，不是正常 24 关胜利。两次 Debug24 全流程、20 次手册纯读检查均通过，Unity 错误列表为空。

Player02 仍有 **516 / 10,746 帧超过 16.7 ms**，其中 106 帧超过 20 ms；平均间隔约对应 **59.70 FPS**。其后 90 秒两个 45 秒诊断窗口的 P95 仍分别为 16.7766 和 16.7681 ms，说明长期历史压力没有消失；这些窗口不改变冻结的完整 180 秒 P95 验收结论。该 Windows 结果可以通过当前指定场景的技术门槛，不能改写为每帧 ≤16.7 ms、所有硬件稳定 60 FPS、macOS 已验收或完整版本已可交付。整体状态由 root 汇总跨平台和交付证据后更新。
