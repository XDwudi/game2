# 平衡模拟器（balance_sim）

为平衡性方案提供数据的离线工具（v0.8 起用，现已升级到规则 p1.1.1）。它直接编译游戏的规则核心
（`DicePrototype/Assets/Game/Core/Rules` 与 `Core/Session`），不修改游戏工程里的任何文件，也不被游戏加载。

p1.1.1 的改动集中写在下面“p1.1.1 的改动与测量”一节；更早版本的小节保留原文，凡与 p1.1.1 不一致的地方以该节为准。

## 它做什么

| 模式 | 用途 |
| --- | --- |
| `verify` | 把模拟器内部的快速计分模型与游戏真实的 `ScoreCalculator.Evaluate` 逐次对拍，并打印每张控制器、每个首领减益、每种计分效果的覆盖次数 |
| `cards` | 每张控制器在两个参照构筑里的等效倍率（有它 ÷ 没它的期望整关得分）与触发率；成长卡各列两行（成长 0 与标明的中期成长值）；改骰面的卡另列“正常打 6 关 / 12 关之后”两行 |
| `scen` | 手工搭好的场景：骰面养成的终态、乘区四件套、裸装过关概率，以及 v1.0 各新流派的成型状态 |
| `run` | 机器人通过真实的 `GameSession` 用合法命令打完整局，输出逐关到达率、通过率、金币收支、购买统计、死亡分布，以及 v1.0 的关卡类型、首领减益、战利品、高压挑战统计 |
| `trace` | 把机器人指定种子的一局命令录成 JSON。`--steps` 指定前缀长度，`--full` 录到胜利或失败，供打包后的游戏回放并截图 |

## 运行

需要 .NET SDK 10。`BalanceSim.csproj` 显式编译真实 Core/Rules 与 Core/Session（仅用 ConfigValidationRelaxed 替代钉死发布数值的校验）；关闭共享编译服务，避免其他 worktree 的编译服务权限干扰。从仓库根目录执行（`--threads` 限制并行度，默认最多 8）：

```powershell
# 若要求所有缓存也留在本 worktree，先设置：
$env:DOTNET_CLI_HOME = "$PWD/tools/balance_sim/.dotnet"
$env:NUGET_PACKAGES = "$PWD/tools/balance_sim/.nuget/packages"
$env:DOTNET_CLI_TELEMETRY_OPTOUT = "1"
$env:DOTNET_GENERATE_ASPNET_CERTIFICATE = "false"
$env:DOTNET_ADD_GLOBAL_TOOLS_TO_PATH = "false"
New-Item -ItemType Directory -Force evidence/v111/balance | Out-Null
dotnet build tools/balance_sim/BalanceSim.csproj -c Release
$sim = "tools/balance_sim/bin/Release/net10.0/BalanceSim.dll"
dotnet $sim verify --n 300000 --out evidence/v111/balance/verify_p111.json --log evidence/v111/balance/verify_p111.log
# cards / scen 是独立分析命令（p1.1.1 下能运行，W5a 只各跑过一次小样本确认不报错，没有留证据）。
dotnet $sim cards --hands 3000 --threads 8 --out evidence/v111/balance/cards_p111.json --log evidence/v111/balance/cards_p111.log
dotnet $sim scen --hands 2000 --threads 8 --out evidence/v111/balance/scen_p111.json --log evidence/v111/balance/scen_p111.log
# 日常 smoke：20 局；300 局由协调者另行排期。
dotnet $sim run --first 5000 --seeds 20 --threads 4 --out evidence/v111/balance/run_p111_smoke.json --log evidence/v111/balance/run_p111_smoke.log
dotnet $sim trace --seed 5000 --steps 80 --out evidence/v111/balance/trace_p111_5000.json --log evidence/v111/balance/trace_p111_5000.log
```

- 所有模式都接受 `--config <路径>`（模拟候选数值）和 `--log <文件>`（把屏幕输出同时写成 UTF-8 文件）。
  不要用 PowerShell 的 `>` 重定向来存日志（中文会变成乱码），也不要接 `Select-Object -First N`（进程会在写出 JSON 之前被杀掉）。
- 一次 300 局的 `run` 在 8 线程下约 20–40 分钟；结果与线程数无关（每个种子自成一局）。
  p1.1.1 实测：20 局、4 线程用了约 3.5 分钟，平均每局 31.3 秒（最慢的一局 119 秒，时间几乎都花在商店估值上）；按此推算 300 局在 4 线程下约 40 分钟（推算，未实跑）。
- 结果里的 `NaN`（例如空集合的中位数）在 JSON 里写成 `null`。

### 实测用的两个开关（p1.0.0 实测报告加的；本轮 W07 不运行）

```powershell
# 减益对照实验：每个首领关开打前，拿这一局此刻的构筑，把本周期池子里的每个减益都套一遍，记下“实力掉了百分之几”
dotnet $sim run --first 5000 --seeds 300 --threads 10 --lab --out evidence/v11/balance/run_lab_5000.json --log evidence/v11/balance/run_lab_5000.log
# 会准备的玩家：进首领关之前，按即将遇到的减益重排控制器顺序（只影响“最左失效”这一类）
dotnet $sim run --first 5000 --seeds 300 --threads 10 --prepared --out evidence/v11/balance/run_prepared_5000.json --log evidence/v11/balance/run_prepared_5000.log
```

- `--lab` 不改变机器人的任何决定（同一批种子的通关结果与不带它时相同），只在 JSON 里多出 `bossLab`，日志里多一张“modifier lab”表。
  这是**同一批构筑对全部减益**的比较，没有“强构筑才走得到后面、才遇到重减益”的选择偏差。
- `--prepared` 会改变对局（调序是真实命令），所以与普通机器人按种子成对比较，见 `v10_report_tables.py paired`。
- p1.1.1 另有一个只用于测试的开关 `--grant I13,C154`：每局开局就持有列出的道具 / 卡牌（按会话自己的办法造实例）。它用来走到机器人平时很少碰到的机制（钥匙串解锁），**不用于任何平衡测量**。
- `--lab`、`--prepared`、`trace --full`、`cards`、`scen`、`probe` 在 p1.1.1 下各小样本运行过一次（均无报错、无被拒命令、规划自检 0 不一致），没有留证据文件。`v10_report_tables.py` 没有在 p1.1.1 的输出上运行过。
- 实测报告的表由 `v10_report_tables.py` 的 `pool / tension / gold / bosspool / pressure / lab / paired / cardwin / diversity` 模式生成，
  除 `lab`、`paired` 外都可以一次给多份 `run` 的 JSON，按局合并。
- 历史回放使用 `--steps N` 截取前 N 条命令。p1.1.0 发布验证用 `trace --full --seed 5000 --out <整局记录.json>`。模拟器逐步重放命令，记录重排顺序、终局关号与阶段，以及首次进入各类界面和领取战利品的截图顺序，供 Windows 玩家包逐项核对。
  Windows 包生成后，在仓库根目录运行 `python tools/replay_v11.py --trace <整局记录.json> --out evidence/v11/replays/final`。运行器在新目录解压已核验的包，依次回放六套风格，保存截图、玩家日志和发布索引。

### 关卡目标候选与校准

```powershell
# 24 个数 = 第 1..24 关的普通目标；高压关的 riskTarget 自动 = 普通目标 × 1.5
python tools/balance_sim/make_targets.py --name v111_t1 --targets 160,320,500,...
# p1.1.1 的常用写法：前三关锚点不动，只给第 4..24 关的 21 个数；--keep-anchors 在前三关被改动时报错
python tools/balance_sim/make_targets.py --name v111_t1 --from 4 --keep-anchors 160,320,500 --targets 740,...
dotnet $sim run --config tools/balance_sim/candidates/v111_t1.json --first 5000 --seeds 300 --threads 8 --out evidence/v111/balance/run_v111_t1.json --log evidence/v111/balance/run_v111_t1.log
python tools/balance_sim/calibrate.py summary evidence/v111/balance/run_p111_300.json evidence/v111/balance/run_v111_t1.json
python tools/balance_sim/calibrate.py predict --fit evidence/v111/balance/run_p111_300.json --base evidence/v111/balance/run_p111_300.json --from 4 --targets 740,...
python tools/balance_sim/calibrate.py solve   --fit evidence/v111/balance/run_p111_300.json --base evidence/v111/balance/run_p111_300.json --from 4 --win 0.30 --boss-gap 0.03 --round
```

- `make_targets.py` 只改 `normalTarget` 与高压关的 `riskTarget`（× 3/2），其余原样复制，写到 `tools/balance_sim/candidates/`。
  p1.1.1：源配置必须是 p1.1.1；每个目标必须是偶数（规格 §11；× 1.5 与首领减益的 × 150% / × 200% 才是整数），奇数直接报错；没改到的关也按同样的规则复查一遍；模拟器自己的宽松校验也检查这两点。
  三个模式都在 20 局冒烟的输出上跑通过（`summary`、`predict`、`solve`）；`solve` 的 `--from 4` 让前三关保持锚点。20 局的拟合没有统计意义，只说明脚本能跑。
- `calibrate.py summary` 汇总若干次 `run`：通关率、每四关一段的死亡占比、逐关与分关卡类型的通过率、高压接受率、最后一关（终局减益生效前）的实力 ÷ 目标。
- `calibrate.py predict / solve` 是挑候选时用的纸面估算，**只用于选候选，不是证据**，每个候选都要真跑：
  用已有模拟拟合“实力 ÷ 目标 → 通过率”（全部 24 关），再把每个种子按新目标重走一遍。高压关按机器人自己的规则重新决定接不接
  （保守实力 ≥ 1.3 × 1.5 × 目标）；首领关沿用该种子记录下来的“带减益 ÷ 不带减益”比例。它不知道目标变了以后机器人会怎样改变购物。
  `solve` 按目标反推：给定通关率，让六个四关段的死亡数相等、首领关比同段其他关难 `--boss-gap`、任何一关不低于 `--min-clear`。
- `make_candidate.py`、`fill_plan.py` 与 `report_tables.py` 是 v0.8 方案用的旧脚本，输入是 `baseline/` 里冻结的旧配置。

## 快速计分模型与对拍（`Fast.cs`）

**p1.1.1 的公式与状态见“p1.1.1 的改动与测量”一节**；本节以下是 p1.0.0 / p1.1.0 写下的覆盖范围与判定办法，判定办法至今不变，
但其中的数值口径（颜色倍率、黄金翻倍、成长值 0–200、等级 0–8、`GrowthZero`、C90 等）已被 p1.1.1 取代。

`Build.Score` 用 double 复刻 `ScoreCalculator.Evaluate`。p1.0.0 覆盖：

- 全部 150 张控制器：留池骰、本手已投次数、剩余投掷、本关剩余提交、永久骰数量、逐骰事实（纹理、整骰同色、整骰同点、对面点数、临时骰）、
  再计、牌型倍率加值、场外红人与锦上添红的红组数量、成长值、百变模仿与被复制卡共用成长值、昙花一现的衰减、
  一掷千金按冻结钱包从左到右占用预算（只有前 ⌊钱包 ÷ 3⌋ 个来源触发，附魔也只算这些来源的）。
- 首领减益的全部计分效果（`ModFx`）：八种封印、禁顺、小打小闹、不重样、半吊子、打回原形、褪红、褪蓝、慢热、强弩之末、釜底抽薪、成长归零、附魔沉默。
- 本关失效的控制器（不是来源，但仍计入控制欲、草根逆袭的件数与留白的占用栏位）、蓝色浪潮、灵光一闪、关卡类型、背包道具数、普通栏位数、本关已用过的主牌型。
- 能力覆盖集合 `HitSet` 是 192 位，只表示该能力至少一个来源触发；`lastSourceHits` 按来源索引保留每个实例的触发，不能用能力集合计副本数。

`verify` 的判定：快速值与真实计分的**精确有理数**（`scoreNumerator / scoreDenominator`）相对误差 ≤ 1e-9，向下取整后的分数一致，
主牌型一致，并且**触发能力集合、按顺序排列的来源实例 ID**与真实计分完全一致。
p1.1.0 随机构筑按六类轮换：无重复对照、双持、三持、双持加 C41、三持加两张相邻 C41、放回抽样。定义、附魔、状态与位置仍随机，总张数最多 10。
`duplicateBuilds` 是至少一个定义出现两张的构筑数，`twoCopyBuilds` 是存在恰好两张的定义，`threeCopyBuilds` 是存在至少三张的定义；后两项可重叠，不能相加。
`duplicateMimicBuilds` 为含重复且含 C41，`duplicateCopiedByMimicBuilds` 要求有效 C41 正在复制一个重复定义。
每张计分类卡还必须在至少两个真实副本存在的样本中出现并触发；覆盖缺项则失败。成长卡带 0–200 的独立成长值，昙花一现 0–3；1–10 颗骰子，随机点数 / 颜色 / 纹理 / 黄金 / 玻璃 / 骰面权重 / 临时骰，含整骰同色与整骰同点；
留池骰 0–5 颗；已投 1–6 次；剩余提交 1–4；永久骰数量 0–8；钱包 0–129；提交栏容量一半取自控制器、一半随机 1–8；
五分之三的样本带一个随机首领减益（39 个等概率）及它造成的失效控制器，另有六分之一的样本再随机失效一两张；
随机的关卡类型、背包道具数、普通栏位数、本关已用牌型、红 / 蓝浪潮、灵光一闪；
三分之二的样本把朝上的面往某种形状凑（同点、对子、三条、顺子、回文、全偶数、+1 递增、恰好一对；颜色交替、红在左、单色），保证牌型类与顺序类卡片有足够触发次数。

输出末尾三张覆盖表，任何一项为 0 则判失败：每张控制器“出现 / 触发”；每个首领减益“出现 / 去掉它之后精确分数不同”；
每种计分效果“出现 / 真的起了作用”（例如禁顺要求去掉减益后确实有顺子）。另有“失效控制器改变了结果”的计数。

## p1.1.1 的改动与测量

工作包 W5a（`docs/specs/v111/briefs/W5A_SIMULATOR.md`），规则依据 `docs/specs/v111/RULES_DELTA.md`。实施备注在 `docs/specs/v111/W5A_NOTES.md`。

### 快速计分（`Build.Score`）

得分 = B × H × R × (1 + A) × M × G，与规格 §2 一一对应：

- **A（加成合计，百分单位）**：颜色（全蓝 25 + 50 × 等级、全红 50 + 50 × 等级；`NoRed` / `NoBlue` 只清掉对应的颜色项）、每颗提交的黄金面 +50（封印骰与 `PipsOnly` 下照给）、
  触发的加成卡（固定值直接读配置的 `additiveBonus100`；C19、C47、C49、C63、C137、C139、C141、C147、C148、C150、C151、C152 各有自己的算法）、加成类成长卡、每个触发来源的倍率附魔 +150。
- **M（控制器侧连乘）**：固定乘法卡读配置的 `scoreMultiplier100`；C49 没有 5 点时每个来源 ×1/2；C53、C71、C87、C89、C103（≤3 颗 ×3、4 颗 ×2）、C155（四个 4 点 ×2，再有两个 1 点 ×4）；乘法类成长卡。
- **成长值** = 起步 + 追赶 + 事件累计；`GrowthHalf`（返璞归真）时每个来源的事件累计先整除 2。`Build.From` 为每个技能预先算好“全值”与“半值”两套（`gFull` / `gHalf`）。
- **C137** 逐来源读状态所有者的明星点数（`star137`，0 = 未抽，不触发），与 C138 一样按来源记触发与附魔；**C156** 读 `Build.stageScore` / `stageTarget`（冻结累计分与有效目标）。
- 黄金面不再让骰子贡献翻倍；玻璃仍然 ×3。C90、C128、C145 已移除；C154 不计分。
- `Build.lastAdditive` 是上一次 `Score` 的加成合计，`verify` 用它与真实计分的 `additiveTotal100` 逐例核对。

### `verify`

判定标准不变（精确有理数相对误差 ≤ 1e-9、取整分数、主牌型、触发能力集合、来源实例顺序），另加一条：加成合计必须等于 `additiveTotal100`。
随机构筑新增：成长卡的事件累计 0–1200（含奇数，检验减半取整）与追赶值（0–7 个周期步长，四分之一样本取 0–400 的任意值）、
C137 明星点数 0–6、养成卡的改面计数 0–24、骰面的 `cultivated` 标记、牌型与颜色等级 0–12、背包里的钥匙串（剩余 1–3 次）、
冻结累计分与有效目标（三分之一从 0 起、三分之一任意、三分之一落在半分线上下 ±1；四分之一样本用奇数目标）。
朝上面的引导形状多了一种（前四颗凑 4 点、接着两颗凑 1 点），用来覆盖 C155 的两档；这是增加引导，没有缩小任何随机范围，也没有跳过任何卡。
覆盖表里所有以 `v111 ` 开头的条目（新乘区、新状态、各张新卡的分支、C141 的四个倒计时值）与原来三张表一样，任何一项为 0 即判失败。

实测（`evidence/v111/balance/verify_p111.json` / `.log`，300000 例）：不一致 0，最大相对误差 1.3e-15；122 张计分卡全部“出现且触发”，
最少的是 C11（触发 47 次、两张同时触发 8 次）与 C86（49 / 10）；首领减益里改变得分次数最少的是 B21（148 次）；计分效果里最少的是 `NoRepeatHand`（148 次）；
`v111` 条目里最少的是 C155 ×4（80 次）。28 张不计分的卡（配置的 `nonSubmitControllerIds` 加 C41）不要求触发。

### 机器人的新行为

| 机制 | 做法 |
| --- | --- |
| 成长卡 | 无上限、按新单位投影，见“成长卡怎么估值”。报价上的追赶值随卡继承 |
| 乘法卡唯一 | 已持有的去重卡（`cfg.shop.uniqueControllerIds`）不估值、不购买、不领取；货架本身也不会再出它 |
| 养成卡免栏位 | 栏位占用一律用 `ControllerRules.OrdinaryUsed(列表, cfg)`；“放不放得下”按“买入后的卡列”判断（新卡在最右），所以第一张养成卡在栏位已满时也能直接买，卖掉免栏位的那张不算腾出位置 |
| 骰面改造 | 货架、赠礼与自选共用 `PlanUpgrade`：按面的改造一次给一颗骰的两个面。镀金（U06）用算式估值而不抽样，其余实测；每店自选至多 2 笔（U06、U08、U03、U04），见“骰面改造与服务” |
| 镀金加权重 | 估值与骰面投影里，新镀金的面权重 +1（上限 5） |
| 牌型与颜色升级 | 价格与上限读会话报价（基础价 + 等级，12 级封顶），估值不变 |
| 玻璃 | 投掷不再碎。实力估计里，提交过的玻璃骰每颗 15% 概率碎掉，本关余下的手牌就没有它；买“脆化”时再按视野内它还活着的时间加权（活着的增益与碎掉后少一颗骰的损失） |

## 机器人怎么玩

- 对局：每次投掷后，对“锁哪些骰、是否提交”做抽样前瞻（最多看两次投掷），目标是尽快凑够本关剩余分数。
  它只看当前可见的骰面，不读取任何随机数状态；规划用自己独立的随机流。
  前瞻里每一次估分都带着真实的提交上下文：这次提交后**留在池里的骰子**、**已投次数**、**剩余投掷**、**本关剩余提交次数**，
  以及 p1.0.0 的**首领减益、失效控制器、本关第几次提交、本关已用牌型、背包、空栏位**。
  `run` 会统计“规划器对自己选定的提交给出的分数”与真实会话结算的分数是否一致（不含错乱乘积），输出在 `planner self-check` 一行；首领关同样计入。
- 商店：对每件商品，用同一批模拟手牌估算“买了之后的关卡得分 ÷ 现在的关卡得分”，按每金币收益排序购买。
  估值同时看平均手和较差的一手（第 25 百分位），所以高方差的卡不会按好运气估价。
  下一关看起来危险时不留钱，安全时为利息留钱；超过利息上限的余钱只要有提升就会花掉。
  买了之后剩下的钱会低于留钱线的商品不做估值（购买规则本来就不会买它，省掉估算时间）。
  估值用的模拟手牌按本关的提交位置轮转（第 1 / 2 / 3 次提交），所以渐入佳境、开门红、移花接木、慢热 / 强弩之末这类“看第几次提交”的效果按整关平均计入。
- 栏位：用本局的 `controllerSlots`（开局 5）。普通栏位用满、至少还剩 3 关时，把“扩充栏位 O08”当作每金币 0.10 收益的商品。
- 栏位已满时换卡：只尝试卖掉“拿掉后损失最小”的两张。p1.0.0 起，总件数到 10 件上限时也按同样的办法换卡（此时不占栏位的卡也可以被换掉）。
  百变模仿的位置：自己持有的构筑和货架上的百变模仿仍然全位置搜索；估其它商品时只试“当前位置”和“紧贴新卡左侧”。

### p1.0.0：关卡周期

- **关卡选择**：读取会话给出的周期面板（`CycleView`）与入关预告（`EntryView`、`EffectiveCapacity`、`InitialRolls`、`InitialSubmissions`）。
  首领关用“带减益、带失效控制器、按预告的预算”估一次实力，再用“没有减益”估一次，两者都记进日志。
  机器人自己用 `ControllerRules + StageRules` 算出的预算若与会话预告不一致，会计数并在 `run` 里报告（应为 0）。
- **高压挑战**：保守实力（每手都按第 25 百分位）≥ 1.3 × 高压目标（= 1.5 × 普通目标）时才接。`run` 报告接受率、接受后的通过率、逐关接受率。
- **首领关对局**：规划器的计分模型带着减益（封印、禁顺、小打小闹、不重样、半吊子、等级归零、褪色、减半、只计点数、成长归零、附魔沉默、失效控制器）；
  预算类减益（投掷、提交、容量、目标）直接读会话里的实际数值。`MustFill`（满员）：只考虑恰好 min(容量, 存活骰子) 颗的提交。`NoItems`（徒手）：只用破咒符。
- **提交顺序**：对“桌面上真实的这一手”，4 颗以内穷举全部顺序；5 颗以上用构造法各试一个候选——按价值把骰子分配到“再计 / 封印”栏位
  （一马当先、压轴好戏、中流砥柱；出头鸟封第 1 位、隔行封印封第 1/3/5/7 位：价值最低的骰子放进被封的位置）、每颗骰子轮流当第一颗（首当其冲、大数开路、排头兵）、
  不断增加的等差三连、红蓝相间（交替排）、泾渭分明（红在左）、对称美学（成对镜像）、顺藤摸瓜（切成若干 +1 递增链）——真正提交前再用两两交换做一次爬山。
  得分相同的顺序里，再按养成偏好挑一个（潜移默化：第一颗放点数大且同点面最多的；点金手：最后一颗放还没镀金的大点；移花接木：好面在前、差面在后）。
  **前瞻里抽样出来的未来手牌**只用构造法（不穷举，第一颗只试点数最大、贡献最大、以及首当其冲时最大的红 / 蓝骰）：穷举会让带顺序卡的构筑慢一个数量级。
  只有再计 / 封印栏位效应的构筑（没有上述“图案”卡）始终是精确分配。

### 成长卡怎么估值

p1.1.1（规格 §5）：成长卡的牌面值 = 配置起步值 + 追赶值 + 事件累计，三者都是整数（加成与乘法卡是百分单位，基础分卡是整数分），**没有上限**。
货架或战利品报价上的卡带着追赶值，估值时原样继承（`WithController`）；事件累计从 0 开始。
商店估值时，对构筑里的每张成长卡（已有的和候选的一视同仁）先把事件累计推到

> growth′ = 当前事件累计 + 每关事件数 × 每次事件的增量 × 视野，视野 = min(剩余关数, 6)；下一关看起来危险时取 2

再算实力（`Runner.ProjectedGrowth`）。既然没有上限，视野就是唯一的刹车：视野取 6 关意味着后期才买的成长卡不会按“养到通关”估值。
每关事件数用机器人看得到的量估（S = 最近各关平均用掉的提交次数）：

| 卡 | 类别，起步 / 每次 | 每关事件数 |
| --- | --- | --- |
| C55 积少成多 | 基础分，+12 / +3 | S |
| C56 深蓝 | 加成，+1 / +0.4 | S × 模拟手牌里“没有红面”的提交占比 |
| C57 红火 | 加成，+1 / +0.8 | S × 模拟手牌里“红组 ≥ 3”的提交占比 |
| C58 老当益壮 | 乘法，×1.25 / +0.15 | 1 |
| C59 余勇可贾 | 基础分，+12 / +6 | 最近各关平均剩余的提交次数 |
| C60 千锤百炼 | 加成，+1 / +0.5 | 最近各店平均的骰面改造**笔数**（货架、自选、赠礼、战利品；双面算一笔） |
| C61 学无止境 | 加成，+1 / +0.5 | 最近各店平均购买的牌型 / 颜色等级数 |
| C62 熟能生巧 | 基础分，+12 / +1 | 模拟手牌的平均投掷次数 × S |
| C51 人员流动 | 加成，+1 / +0.8 | min(1, 最近各店平均卖出的卡牌数)（每店只算第一次） |
| C125 抛光匠 | 乘法，×1.25 / +0.2 | 已过各关里“本关刷新了本局最高单手”的占比（先验 0.7） |
| C129 屠龙者 | 加成，+1 / +2.5 | 视野内的首领关数 ÷ 视野（终局首领不算，它之后没有关卡） |

`run` 在每个首领关前另记一次“去掉这张成长卡之后的实力 ÷ 带着它的实力”（`growthShare`，BX-17 用）。

## 已知局限（解读数据时必须考虑）

1. 机器人不会经营“养成型”控制器。v0.6 的 C07、C15、C26、C36、C37、C38、C43 它只按当下收益估值；p1.0.0 的骰面养成卡按上面的投影估值，
   但它在对局里只做一件事来配合：得分相同时挑一个更利于养成的提交顺序。它不会为了养成多提交、换打法或专门留骰。成型后的强度在 `scen` 里单独测量。
2. 机器人不使用：光滑 / 粗糙 / 随机变形骰面，遥控骰子、大数多来、小数多来，以及道具槽、折扣、免费刷新、增加道具、删除骰子等服务。
   达标后它立刻结束本关，不会为了成长或养成而多提交。
3. 机器人胜率不是玩家胜率。它适合比较两套数值的相对差异和曲线形状，不能直接当作“玩家有百分之多少能通关”。
4. p0.9.0 起的盲区：
   - **C100 祭坛永远不买**（若因故持有，会把它排到最右，不摧毁任何卡）。它的强度只在 `cards` 里按假定成长值列出。
   - 成长卡只在商店估值时被“预支”成长；对局里的手牌策略不会为了成长去改打法
     （不会为深蓝刻意交全蓝、为红火凑红组、为熟能生巧多投、为连庄维持同一主牌型、为余勇可贾省提交）。
   - 依赖它不会做的操作的卡被低估或永远不触发：C91 纹理大师（不买光滑 / 粗糙面）、C103 精兵简政（不删骰子）、
     C92 纯色主义与 C93 始终如一（不会刻意把一颗骰子做成同色 / 同点）、C90 玻璃心（很少买玻璃骰）、C60 千锤百炼（买骰面改造少）。
   - 前瞻最多看两次投掷：有“再给一次”、投掷附魔或“再来三次”而剩余投掷 ≥ 3 时，对“孤注一掷 / 越挫越勇”只是近似。
   - 栏位已满时只试两张“最不重要”的卡作为被换下的对象。
   - 实力估计里“只在某一次提交生效”的卡（C68、C102、C153、C127、C150 的后几手）计入平均实力，但基本不进入“较差一手”的估计。
5. p1.0.0 新增的盲区：
   - **首领减益只影响当关的打法，不影响长期构筑**。机器人不会因为“本周期的首领封红”而提前避开红色构筑；它只在下一关就是首领且看起来过不去时，
     才按带减益的实力给商品估值，其余时候用贿赂首领 / 破咒符 / 替罪羊这三样对策。
   - **会话类减益里的长期代价没有进入打法**：削级（每次提交主牌型永久 −1 级）、苛税（每颗提交骰 1 金币）、停滞、白干、过路费。
     机器人不会为了少降级 / 少交税而少提交或换牌型，只有削级会触发破咒符。
   - **提交顺序是近似搜索**：5 颗以上不是穷举，构造法 + 爬山可能漏掉多张顺序卡叠加时的最优排法；前瞻阶段（决定锁哪些骰）用的是不带爬山的估值，对顺序卡略偏保守。
   - **高压挑战只看实力余量**，不看金币需求、高压锅 / 赏金猎人的收益，也不为屠龙者、高压锅刻意保留构筑。
   - **道具**：I09 不会留给最强的一手，只按上面的条件用；机器人不为囤积居奇刻意留道具；
     不买道具槽，所以百宝袋 / 杂货郎的道具常因背包满而拿不到（它会用掉一个腾位置）。
   - **金币类卡**：一掷千金、富甲一方、有钱真好按“估值那一刻的钱包”计入，机器人不会为它们调整花钱节奏。
   - **吹玻璃 / 玻璃流**：只有“下一颗变玻璃”的即时收益和一个固定折扣，没有模拟骰子逐关碎掉的过程。
   - **滥竽充数、点化、无心插柳、附魔台**的随机结果只有固定估值；机器人不会因为栏位空着就多买滥竽充数。
   - 单面的骰面改造（U08–U11）低于噪声门槛，很少被购买；多次购买才成型的骰面路线它走不出来。
   - `cards` 的 `@s6 / @s12` 行不模拟金币、成长值、玻璃碎裂与随机的关末效果；每关固定打满 3 手（真实对局里机器人平均只用 2 手左右，养成更慢）。
6. `ConfigValidationRelaxed.cs` 取代了游戏里钉死数值的 `Validate()`，只在模拟器里生效；p1.0.0 起它也提供 `Modifier`、`Loot`、`ModifierEffects`，
   并检查周期结构、首领池、战利品种类与目标的整除性。p1.1.1 起还检查：普通目标为偶数、高压目标恰为普通的 3/2、去重名单与追赶步长等新字段存在。
7. p1.1.1 新增的盲区。**会让实力被低估的**：
   - 成长卡只按 6 关视野估值、打法不配合（不为深蓝交全蓝、不为连庄保牌型、不为抛光匠冲高分、达标就结束本关），真实玩家养得更快更久。
   - 骰面培养只用了四种自选改造，其中只有镀金是按算式稳定购买的；染色、精雕仍受噪声门槛限制，配重、镜像、削点不进自选。它不会围绕某个牌型把整套骰面改成型。
   - 牌型与颜色升级只在实测增益过噪声门槛时买，不会有计划地把一个牌型升到 12 级。
   - 规划器的前瞻不知道“已锁的骰子可以解锁”；钥匙串只在金币富余或下一关危险时才买，解锁只在事后比较时用，冒烟里很少发生。
   - C137 在商店里按随机点数估值，不会因为“这一关的明星是几点”而换打法之外的构筑；C156 在估值时每关只按手牌顺序累计，不会故意压低前几手。
   - 不买祭坛；不使用 U01 / U02 / U07、I03 / I04 / I05；养成卡免栏位只影响“放不放得下”，机器人不会为了它调整卡列顺序。
   - 高压挑战仍只看实力余量；首领减益仍只影响当关打法。
   **会让实力被高估的**：
   - 成长与骰面投影用的是平均速率，没有方差；C54 的投影用“相邻两手同牌型”的独立概率，实际换牌型往往成串出现。
   - 镀金的算式假设黄金面的收益与其它加成相加、且每颗骰被提交的概率相同；没有扣除“权重变大后别的面更少出现”的影响（对顺子、杂牌这类需要多种点数的构筑偏乐观）。
   - 玻璃骰碎掉之后“这一局永远少一颗骰”的长期损失，只在购买脆化时按视野加权计入，入关实力估计不含（它只模拟本关之内的碎裂）。
   - 入关实力估计是“每手都按最高分打”的手牌 × 提交次数；真实对局里机器人达标即停，所以 `score ÷ target` 远低于 `power ÷ target`，这不是误差，但读数时要分清。
   **方向不定的**：
   - 实力估计每次只抽 32 手；后期构筑的单手分布很宽，单个种子的 `power` 噪声不小，校准应看中位数与分位数。
   - 裸装起手：规划器“每手打最高分”的平均手约 166–171 分（`cards` / `scen` 各一次小样本），精确动态规划的最优是 184.6（`opening_dp.py`），即机器人的起手打法约为最优的九成；
     20 局冒烟里第 1 关过关 19 局。样本都小，只能说明量级。

## 裸起手精确动态规划（`opening_dp.py`，V1.1.1）

独立的 Python 脚本，不依赖上面的 C# 模拟器。它只覆盖“没有任何卡的起手”：5 颗标准骰（1、4 点红面），每手最多 3 投、锁定不可逆、
提交已锁定的骰子，0 级牌型，无控制器 / 道具 / 骰面改造。用精确分数求每手期望分最大的策略，再导出最终手牌分布。

    python tools/balance_sim/opening_dp.py --rules p111 --targets 160,320,500
    python tools/balance_sim/opening_dp.py --rules p110 --targets 300,600,1000 --json
    python tools/balance_sim/opening_dp.py --rules p111 --blue 1.5 --red 2 --red-group 1,2,3,4.5   # 自定义倍率

输出：最优打法每手期望分；最终手牌占比（全蓝 / 全红 / 仅红组收益 / 没有任何颜色收益 四项互斥、合计 100%，红组 3 颗以上、含顺子、没交满另计）；
“不看颜色的玩家”（按关闭颜色的规则求最优，再用真实规则计分）的期望分、占最优的百分比及平局取法造成的范围；三手独立累计 ≥ 目标的概率。
各指标的精确口径见脚本 docstring。三手达标假设每手都用同一个“期望分最大”策略，不是按目标调整的最优策略，所以“不看颜色”在低目标上可能略高于“最优”。
测试：`python -m unittest tests.test_opening_dp -v`（含 BX-03 门槛断言）。
